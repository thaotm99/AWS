<Scene id="en-s1" label="Part 1/4" title="A cache in front of the database" questions={["exam4_q12", "exam3_q33", "exam5_q37", "exam4_q50", "exam4_q32", "exam6_q6", "exam1_q29"]}>

**ElastiCache** is a managed in-memory data store with sub-millisecond response times. The most common usage pattern is **cache-aside**: the application queries the cache first; if the data is not there (a cache miss), the application reads from the database and writes the result to the cache with a TTL. Try five ShopViet scenarios:

<CacheSim client:visible />

ElastiCache fits two kinds of workload: **heavy read traffic** (the same data is queried repeatedly) and **compute-intensive results** (results that take a lot of resources to compute, such as leaderboards). ElastiCache does not solve heavy write traffic, does not run complex JOINs and does not perform ETL.

For data on DynamoDB, there is also **DAX** (DynamoDB lesson). ElastiCache works with any data source: RDS, Aurora, DynamoDB, or ElastiCache itself acting as a session store.

<Takeaway>Repeated read queries overloading the database: ElastiCache with cache-aside and a TTL. Sessions shared across servers: ElastiCache. Reducing downtime and cache data loss: Multi-AZ with automatic failover.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/4" title="Choosing an engine: Redis and Memcached" questions={["exam6_q47", "exam5_q65", "exam1_q29", "exam4_q32"]}>

ElastiCache supports three engines: **Valkey**, **Redis OSS** and **Memcached**. Valkey and Redis OSS support many data structures and high availability features. **Memcached** is simpler but multithreaded. Send the same sequence of commands to two identically configured nodes, then choose ShopViet's requirements:

<CacheEngineSim client:visible />

Examples: caching the results of slow JOIN queries on RDS while making use of many cores: Memcached. Real-time leaderboards, finding the nearest store, requiring failover: Redis OSS. For leaderboards on DynamoDB data, DynamoDB + DAX is also an in-memory option.

<Takeaway>Multithreaded, simple key-value: Memcached. Sorted sets, geospatial, pub/sub, replicas, Multi-AZ failover, backups: Valkey or Redis OSS (comparison for node-based clusters; with ElastiCache Serverless, Memcached also supports backup and restore).</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/4" title="Choosing a tool for each data task" questions={["exam5_q12", "exam1_q26", "exam1_q53", "exam5_q58", "exam5_q6", "exam4_q11", "exam2_q15", "exam6_q26"]}>

ShopViet's data is stored in a data lake on S3. Each task has a best-fit service:

- **Athena**: SQL queries directly on files in S3, serverless, billed by the bytes of data scanned. Suits ad-hoc queries.
- **Redshift**: an MPP data warehouse for reports and dashboards that run on a schedule. Has a **Serverless** option. **Redshift Spectrum** lets a Redshift cluster also query data on S3.
- **Glue**: serverless ETL and the Data Catalog. **Glue DataBrew**: clean data through a visual interface, with no code to write.
- **EMR**: Spark/Hadoop clusters of the size you choose, used when you need control over the framework and configuration.

Choose a task, run the simulation, then switch to the better-suited tool:

<DataJobSim client:visible />

<Takeaway>Ad-hoc SQL on S3: Athena. Serverless MPP data warehouse: Redshift Serverless, loaded with Glue. No-code data cleaning: DataBrew. Converting recordings to text: Transcribe. Full-text search: OpenSearch. Relationships between users (graph): Neptune. Infrequently accessed data that still needs immediate SQL queries: S3 Standard-IA + Athena.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/4" title="Controlling data lake cost over time" questions={["exam2_q34", "exam6_q26", "exam5_q11"]}>

ShopViet's data lake is split into two zones. The **raw zone** stores the original data as it was received. The **refined zone** stores data that Glue has cleaned for analysts to query. Each zone grows by 1 TB a day. Choose a storage option, then simulate one year:

<LakeCostSim client:visible />

When the data lake needs another copy in a different Region for disaster recovery:

- Enable **Cross-Region Replication** on the bucket. CRR replicates only objects written **after** it is enabled; existing objects need S3 Batch Replication. Starting from scratch with a new bucket is the simplest option.
- Encrypt with **SSE-KMS using a multi-Region key**: the key has a replica in the other Region with the same key material, so the data in both places uses the same set of keys and the same permission configuration.
- Athena can query in the Region that holds the data.

<Takeaway>Original data that must be retained but is rarely read: lifecycle to Glacier Deep Archive. Data that is still queried: keep it in a storage class with immediate access, written in a compressed columnar format (Parquet). Athena cannot read data in Glacier Deep Archive until it is restored.</Takeaway>

</Scene>
