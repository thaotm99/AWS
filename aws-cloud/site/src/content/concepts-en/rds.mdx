<Scene id="en-s1" label="Part 1/6" title="How Multi-AZ and Read Replicas differ" questions={["exam1_q52", "exam5_q25", "exam6_q49", "exam2_q25", "exam3_q63", "exam3_q41"]}>

Write an order, run a report, run an automated backup, then simulate a primary failure and try the two kinds of maintenance:

<MultiAzSim client:visible />

The simulation above is a **Multi-AZ DB instance deployment** (one standby). RDS has a second form, the **Multi-AZ DB cluster deployment** (RDS for MySQL and RDS for PostgreSQL): one writer and **two reader DB instances** in three AZs of the same Region, with **semisynchronous** replication (acknowledgment from at least one reader), and the two readers are both failover targets and **serve read traffic**. Statements in this lesson that "the standby serves no reads" apply to the DB instance form only.

<Takeaway>Multi-AZ DB instance deployment: synchronous replication to one standby that does not serve reads, for fault tolerance; a Multi-AZ DB cluster deployment has two readers in two other AZs that are failover targets and also serve reads; failover works by updating the CNAME. Read Replica: asynchronous replication that serves reads, to offload read traffic. OS maintenance is applied to the standby first; engine upgrades are applied to both at the same time (except RDS for SQL Server, which uses a rolling upgrade). Automated backups and snapshots are taken from the standby, so I/O on the primary is not suspended. A Multi-AZ failover typically takes 60–120 seconds.</Takeaway>

</Scene>

Two further measures reduce the load on the operations team. The accounting system, which runs on SQL Server, uses **RDS for SQL Server Multi-AZ**: AWS manages the standby and failover. To make every new database follow the same standards (Multi-AZ, backups, encryption), databases are created from the same vetted **CloudFormation template**.

<Takeaway>Reports slow the website: a same-Region Read Replica (no replication charge). Too many connections: RDS Proxy. Risk of running out of storage: storage autoscaling. Region-level outage: a cross-Region Read Replica + backups copied to another Region. OS access needed: RDS Custom (note: AWS ends support for RDS Custom for Oracle on March 31, 2027).</Takeaway>

<Takeaway>Aurora has **no separate standby instance**: when the writer fails, Aurora promotes an Aurora Replica (by priority tier 0–15) to be the new writer; if the cluster has no replica, Aurora recreates the primary in the same AZ (typically under 10 minutes, much slower than promoting a replica). So, to improve availability, create an Aurora Replica in another AZ. Aurora Replicas + the reader endpoint serve heavy read traffic and are also failover targets. Fluctuating read traffic: Aurora Auto Scaling. Multiple Regions (up to 10 secondary Regions), RPO typically measured in seconds, RTO in minutes: Global Database. Unpredictable load: Serverless v2.</Takeaway>

Two approaches sound plausible but cannot encrypt the database: creating an encrypted Read Replica (an encrypted replica of an unencrypted instance is not possible) and turning on Multi-AZ (encryption can be enabled only when the instance is created). Part 5 lets you try both directly.

<Takeaway>Encrypting a running database: snapshot → encrypted copy → restore. A Read Replica always has the same encryption state as its source. Encryption in transit: SSL/TLS. Password-less authentication: IAM DB authentication.</Takeaway>

<Scene id="en-s5" label="Part 5/6" title="Configuring copies for reporting and DR" questions={["exam6_q46", "exam2_q45", "exam5_q42", "exam6_q49"]}>

The accounting team needs a copy of the order database (RDS for MySQL, unencrypted) to run reports on. To save money, someone proposes a replica half the size, or reusing the Multi-AZ standby; the security team wants to encrypt the copy while at it. Try each configuration and observe the result:

<ReplicaLab client:visible />

For DR, ShopViet combines two mechanisms in another Region: a **cross-Region read replica** (promoted to a standalone DB instance if the primary Region fails) and **cross-Region automated backups** (RDS copies snapshots and transaction logs to the destination Region as soon as they are ready). The storage type, for example Provisioned IOPS, determines only I/O performance and is not a DR measure.

<Takeaway>Reports: a same-Region Read Replica with the same compute and storage as the source (scale the replica when you scale the source). A replica's encryption follows the source. The standby of a Multi-AZ DB instance deployment serves no reads and stays in the same Region, but automated backups and snapshots are taken from it. DR for RDS: cross-Region read replicas and cross-Region automated backups.</Takeaway>

</Scene>
