Write an order, run a report, then simulate a primary failure and try the two kinds of maintenance:

<MultiAzSim client:visible />

<Takeaway>Multi-AZ: synchronous replication to one standby that does not serve reads, for fault tolerance; failover works by updating the CNAME. Read Replica: asynchronous replication that serves reads, to offload read traffic. OS maintenance is applied to the standby first; engine upgrades are applied to both at the same time (except RDS for SQL Server, which uses a rolling upgrade). A Multi-AZ failover typically takes 60–120 seconds.</Takeaway>

</Scene>

As ShopViet grows, the database runs into more problems: reports slow the website, Lambda opens too many connections, the disk fills up, a Region-level outage. Choose each incident, run it to see the impact, then turn on the matching RDS feature and run again:

<RdsOpsSim client:visible />

Two further measures reduce the load on the operations team. The accounting system, which runs on SQL Server, uses **RDS for SQL Server Multi-AZ**: AWS manages the standby and failover. To make every new database follow the same standards (Multi-AZ, backups, encryption), databases are created from the same vetted **CloudFormation template**.

<Takeaway>Reports slow the website: a same-Region Read Replica (no replication charge). Too many connections: RDS Proxy. Risk of running out of storage: storage autoscaling. Region-level outage: a cross-Region Read Replica + backups copied to another Region. OS access needed: RDS Custom (note: AWS ends support for RDS Custom for Oracle on March 31, 2027).</Takeaway>

</Scene>

Some other ShopViet decisions involving Aurora:

<RequirementPicker client:visible items={[
  { need: "The development team needs a database with production-like data to test new features", answer: "Restore from an Aurora automated backup (or create a clone)",
    why: "Creates a separate cluster from the backup, with no impact on the production cluster." },
  { need: "The exchange rate table is shared by every country, while the order tables are used only within each Region", answer: "Aurora Global Database for the shared table, standard Aurora for the rest",
    why: "Only the data that must be read globally incurs cross-Region replication costs." },
  { need: "A new internal application with unpredictable, fluctuating load", answer: "Aurora Serverless v2",
    why: "Automatically adjusts capacity (ACUs) to the application's load; you pay only for the resources actually used." },
  { need: "A database with very heavy read and write volume, where I/O charges make up most of the cost, requiring predictable costs", answer: "Aurora I/O-Optimized",
    why: "No additional charges for read and write I/O; you pay only for instance and storage usage. AWS recommends this configuration when I/O costs make up 25% or more of the total Aurora cost." },
]} />

<Takeaway>Aurora Replicas + the reader endpoint serve heavy read traffic and are also failover targets. Fluctuating read traffic: Aurora Auto Scaling. Multiple Regions (up to 10 secondary Regions), RPO typically measured in seconds, RTO in minutes: Global Database. Unpredictable load: Serverless v2.</Takeaway>

</Scene>

Disk encryption is only one part. ShopViet's other security requirements:

<RequirementPicker client:visible items={[
  { need: "The database is already encrypted at rest; data in transit from the application to the database must also be protected", answer: "Connect with SSL/TLS", why: "KMS protects data only at rest." },
  { need: "Lambda connects to PostgreSQL without storing a password", answer: "IAM database authentication + IAM role", why: "Lambda gets a short-lived token through its IAM role instead of a password." },
  { need: "Share a copy of the encrypted database with the analytics team's account", answer: "Share the snapshot + grant use of the KMS key", why: "The snapshot must be encrypted with a customer managed key (a snapshot encrypted with the account's default KMS key cannot be shared), and the receiving account must have permission to use that key. <Takeaway>Encrypting a running database: snapshot → encrypted copy → restore. Encryption in transit: SSL/TLS. Password-less authentication: IAM DB authentication.</Takeaway>
