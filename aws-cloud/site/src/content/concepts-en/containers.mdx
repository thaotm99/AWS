Some other MFTECH scenarios:

- An existing worker talks to a message broker over **AMQP** and the team does not want to manage nodes: run the worker on **EKS with Fargate** and move the broker to **Amazon MQ** (a managed broker that supports AMQP).
- A service on ECS is CPU-bound: turn on **Service Auto Scaling** (based on Application Auto Scaling) to increase the number of tasks based on the service's CPU and memory metrics (part 3).

**IRSA and Kubernetes RBAC solve two different problems.** Kubernetes RBAC (granted through EKS access entries or Kubernetes groups) controls who can work with **Kubernetes objects** in the cluster, for example permission to use `kubectl` to view or change a Deployment. RBAC neither grants nor limits permission to call **AWS APIs** such as S3 or DynamoDB. If both the S3 and DynamoDB policies are attached to the node IAM role (instance profile), every Pod on the node has both permissions, whatever RBAC says. To let the UI Pods reach only DynamoDB and the data-processing Pods reach only S3, give each service **its own service account**, mapped to **its own IAM role** through IRSA (the `eks.amazonaws.com/role-arn` annotation goes on the service account; no policy is attached directly to a Pod) or through **EKS Pod Identity**. Sharing one service account across all Pods removes the permission boundary.

<Takeaway>Durable storage shared between tasks: EFS. Scheduled runs: EventBridge Scheduler starts a Fargate task. Jobs longer than Lambda's time limit (15 minutes for standard functions): containers on Fargate. Separate AWS permissions for each Pod: one service account per service, mapped to its own IAM role (IRSA or EKS Pod Identity); Kubernetes RBAC controls only the Kubernetes API. Pods in the Pending state because the cluster is out of resources: Cluster Autoscaler.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/5" title="Scaling in two layers: Pods/tasks and nodes" questions={["exam4_q56", "exam5_q36", "exam3_q20"]}>

<p class="scene-intro">When load rises, you need more copies of the application (Pods or tasks) and more nodes to run those copies; the two happen at separate layers.</p>

During a sale, traffic to MFTECH's web service grows several times over. Scaling happens in two separate layers:

- **The application layer** (number of Pods or tasks). On EKS, the **Horizontal Pod Autoscaler** (HPA) changes the number of Pods in a Deployment to keep CPU near a target (for example 50%). The HPA is a standard Kubernetes API resource; it only needs a metrics source such as the Kubernetes Metrics Server. On ECS, **Service Auto Scaling** changes the service's desired count (target tracking, step scaling, scheduled, predictive, or based on an SQS queue backlog).
- **The infrastructure layer** (number of nodes). On EKS with EC2 nodes, the **Cluster Autoscaler** adjusts the Auto Scaling group's desired capacity when Pods cannot be scheduled; **Karpenter** and **EKS Auto Mode** (built on Karpenter) create new nodes when Pods do not fit on the existing ones. With Fargate this layer does not exist: each task or Pod gets its own capacity.

Try each setup and watch the number of Pods, nodes and Pending Pods:

<ScaleLayersSim client:visible />

Two lessons from the simulation. First, the HPA only adds Pods; when nodes run out of CPU, new Pods stay Pending and the node count stays the same until a Cluster Autoscaler (or Karpenter) is in place. A CloudWatch alarm on the nodes' average CPU cannot see Pending Pods, so it does not replace the Cluster Autoscaler. Second, a Fargate task's CPU and memory are set at the task level in the task definition; changing them takes a new **task definition revision** and a service update. A single task remains a bottleneck with no redundancy; ECS scales horizontally by adding tasks behind an ALB.

<Takeaway>HPA: adds Pods. Cluster Autoscaler / Karpenter: adds nodes when Pods are Pending. EKS with EC2 nodes needs both. ECS: Service Auto Scaling adds tasks; you do not scale by resizing one running task.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/5" title="Amazon EKS on premises: Outposts, Hybrid Nodes and EKS Anywhere" questions={["exam1_q27", "exam1_q11"]}>

<p class="scene-intro">Some companies must run applications in their own data centers yet still want the same container management tools they use on AWS.</p>

Amazon EKS has several deployment options outside a Region. They differ in **where the control plane runs**, **who manages it**, and **what infrastructure runs the nodes**:

- **EKS on AWS Outposts**: Outposts is AWS-managed infrastructure placed in the company's data center. *Extended cluster*: control plane in the Region, nodes on the Outpost. *Local cluster*: both control plane and nodes on the Outpost. In both cases AWS fully manages the control plane.
- **EKS Hybrid Nodes**: the company's existing servers become nodes; the control plane is in the Region, managed by AWS; a reliable connection to the Region is required.
- **EKS Anywhere**: customer-managed Kubernetes management software that runs the whole cluster on the company's infrastructure, including air-gapped environments.

<Takeaway>Workloads and data must stay in the data center while AWS still manages the control plane: an EKS local cluster on Outposts. An air-gapped environment on existing servers: EKS Anywhere (the company operates the cluster). Existing servers with reliable connectivity: EKS Hybrid Nodes. No on-premises requirement and no wish to manage servers: ECS or EKS on Fargate in a Region.</Takeaway>
