Some other ShopViet scenarios:

- An existing worker talks to a message broker over **AMQP** and the team does not want to manage nodes: run the worker on **EKS with Fargate** and move the broker to **Amazon MQ** (a managed broker that supports AMQP).
- A service on ECS is CPU-bound: turn on **Service Auto Scaling** (based on Application Auto Scaling) to increase the number of tasks based on the service's CPU and memory metrics.
- A branch's data must be stored on premises, but Amazon EKS is still required: **Amazon EKS on AWS Outposts** placed in the company's data center (extended cluster: control plane in the Region, nodes on the Outpost; local cluster: both control plane and nodes on the Outpost). **EKS Anywhere** is another option that runs on infrastructure the company manages itself, intended for air-gapped environments.

<Takeaway>Durable storage shared between tasks: EFS. Scheduled runs: EventBridge Scheduler starts a Fargate task. Jobs longer than Lambda's time limit (15 minutes for standard functions): containers on Fargate. Separate permissions for each Pod: IRSA. Pods pending because the cluster is out of resources: Cluster Autoscaler.</Takeaway>

</Scene>
