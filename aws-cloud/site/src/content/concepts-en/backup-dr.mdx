A Multi-AZ deployment keeps MFTech running when one Availability Zone (AZ) fails. However, there must be a plan for when **the entire Singapore Region** goes down. Management asks two questions: "What is the maximum number of orders we can afford to lose?" and "How soon must the system be back?". The two corresponding metrics are:

- **RPO** (recovery point objective): the maximum amount of data that may be lost, measured in time. An RPO of 15 minutes means losing at most 15 minutes of order data.
- **RTO** (recovery time objective): the maximum time from the moment of failure until the system is back in operation.

The smaller the RPO and RTO, the higher the cost. This lesson shows how to choose a level that just meets the requirement.

<Scene id="en-s1" label="Part 1/5" title="Four disaster recovery (DR) strategies for a Region-level failure" questions={["exam4_q41", "exam4_q5"]}>

<p class="scene-intro">A Region-level failure is rare but has a large impact; how much is prepared in advance in the standby Region decides the RTO, the RPO and the running cost.</p>

MFTech chooses Tokyo as its standby Region. The question is which components are kept in Tokyo under normal conditions. The more components are running, the shorter the recovery time and the higher the cost. There are four levels:

1. **Backup and restore**: only backups are kept. When a failure happens, the system is rebuilt from scratch.
2. **Pilot light**: the core (the database) is always running and receiving data. The web tier EC2 instances are off and are started only when a failure happens.
3. **Warm standby**: a scaled-down but fully functional copy is always running. When a failure happens, the system is scaled up.
4. **Multi-site active/active**: Tokyo is a full site, serving users at the same time as Singapore.

Choose a MFTech objective, choose a strategy, then simulate a failure in Singapore. Also try the AMI option: MFTech's web application takes more than 45 minutes to install on an empty instance.

<DrStrategySim client:visible />

An AMI can be used only in the Region that contains it. To launch quickly in Tokyo, **copy the AMI to Tokyo** in advance (the copy steps were covered in the Global Infrastructure lesson). If MFTech operates in several Regions, the AMI must be copied to each of those Regions.

<Takeaway>Backup and restore → pilot light → warm standby → multi-site: RPO/RTO decrease, cost increases. Choose the lowest-cost level that still meets the objective. "A scaled-down, fully functional copy that is always running" is warm standby. To launch EC2 instances quickly in another Region: create an AMI with the application preinstalled and copy it to that Region.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/5" title="Aurora Global Database, cross-Region read replicas and ElastiCache Multi-AZ" questions={["exam2_q61", "exam6_q23", "exam5_q42", "exam4_q32"]}>

<p class="scene-intro">EC2 instances can be launched again from an AMI in minutes, but lost data cannot be recovered; each data store needs its own protection mechanism.</p>

Web tier EC2 instances can be launched again in minutes, but data cannot: lost orders cannot be recovered. MFTech has three data components, each needing its own protection mechanism:

- **Aurora** stores orders: target RPO ≤ 5 minutes, RTO ≤ 15 minutes when the entire Region fails, and the operations team does not want to develop its own scripts.
- **RDS PostgreSQL** for the inventory application: Multi-AZ is enabled, but nothing exists in another Region yet.
- **ElastiCache Redis** stores shopping carts and login sessions: only daily backups.

<DataFailoverSim client:visible />

**Aurora Global Database** replicates at the storage layer to another Region using dedicated infrastructure, with latency typically under 1 second. When the primary Region has an unplanned outage, a **failover** promotes a secondary cluster to be the primary cluster, typically within minutes; RTO is measured in minutes and RPO is typically measured in seconds (depending on the replication lag at the time of the failure). For planned changes, a **switchover** moves the primary Region without data loss; on eligible engine versions, the downtime is typically under 30 seconds. The service also lets users in the secondary Region read data with low latency. Self-built approaches with DMS, manually promoted read replicas or snapshot-copy scripts all work, but they take longer to recover and cost more to operate.

<Takeaway>Aurora needing an RPO in seconds and an RTO in minutes across Regions: Aurora Global Database. RDS that must survive a Region-level failure: a cross-Region read replica (promoted when needed) and copying automated backups to another Region; Multi-AZ only protects against the failure of one AZ. Redis needing low downtime and little data loss: Multi-AZ with automatic failover, not daily backups.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/5" title="AWS Backup: backup plans, backup vaults and cross-Region copy for Amazon EFS" questions={["exam5_q47", "exam5_q64", "exam5_q16"]}>

<p class="scene-intro">Backups must run automatically, on a schedule, and be retained as long as required; AWS Backup manages backups centrally so that no resource is missed.</p>

MFTech's services run on ECS with Fargate and all read and write seller images and invoices on a shared file system. MFTech chooses **Amazon EFS**: a POSIX (NFS) file system that spans multiple AZs and that Fargate tasks can mount directly. Compliance requirements: automatic backups, a copy in another Region, and at most 8 hours of data loss.

**AWS Backup** centrally manages backups for many services (EFS, EBS, RDS, DynamoDB…). The operator defines a **backup plan**: backup frequency, retention period and copy destination. Recovery points are stored in a **backup vault**. Adjust the plan and test it against each kind of incident:

<BackupPlanSim client:visible />

Each kind of incident needs a different setting. A Region-level failure: you need a copy in **another Region**. Leaked admin credentials: you need a copy in **another account**, or **Vault Lock** in compliance mode so that no one, not even the root user, can delete recovery points before they expire (governance mode still lets users with sufficient IAM permissions remove the lock). Vault Lock protects only the recovery points in that backup vault, that is, backups created by AWS Backup or copied into the vault; AWS Backup does not govern backups taken outside AWS Backup. EBS snapshots created directly by a script or the EC2 API are not in the vault, so Vault Lock cannot protect them; to recover such snapshots after an accidental deletion, use a Recycle Bin retention rule ([Storage lesson, part 2](/concepts/storage/ebs-volumes/)). Audits: you need a long enough **retention period**. The RPO is determined by the **backup frequency**.

AWS Backup serves data protection and compliance; it is not a tool for cloning data quickly. When you restore an EBS recovery point, AWS Backup creates a **new volume** from the snapshot. Like every volume created from a snapshot, its blocks are downloaded from S3 to the volume over time (**volume initialization**); during that time I/O latency is higher and the volume does not yet deliver full performance. When the test team needs frequent copies of production data with full performance right away, the fitting option is an EBS snapshot with **fast snapshot restore** (Storage lesson, part 2).

<Takeaway>A shared file system for containers, across multiple AZs, that needs backups in another Region: EFS + AWS Backup with a backup schedule and cross-Region copy. The backup frequency determines the RPO. A copy in another Region protects against a Region-level failure; a copy in another account and Vault Lock protect backups from deletion. Quick EBS copies for a test environment with full performance right away: snapshot + fast snapshot restore, not a restore from AWS Backup.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/5" title="Recovering a single EC2 instance with a CloudWatch alarm action" questions={["exam3_q38"]}>

<p class="scene-intro">Not every system needs a complex DR strategy; for a single EC2 instance, the CloudWatch alarm recover action is usually enough.</p>

MFTech's internal admin page runs on a single EC2 instance. It has few users and needs neither an Auto Scaling group nor a DR strategy. Requirement: when the instance fails, the system comes back by itself within about 10 minutes, at low cost and with no manual intervention outside working hours.

EC2 has two kinds of status checks. The **system status check** reflects problems with the AWS infrastructure the instance runs on (loss of network connectivity, loss of power, hardware or software failure on the host). The **instance status check** reflects problems inside the instance (the operating system hangs, memory is exhausted). A **CloudWatch alarm** that watches a status check can perform an action: recover, reboot, stop or terminate.

<Ec2RecoverSim client:visible />

<Takeaway>A single EC2 instance that must recover automatically at low cost: a CloudWatch alarm on the system status check with the recover action (for supported instance types, simplified automatic recovery is also enabled by default). The instance is moved to a new host and keeps its instance ID, public IPv4, private IP, Elastic IP, metadata and EBS volumes. Instances with instance store are supported only on some instance types (M3, C3, R3, X1, X1e, X2idn, X2iedn), and the data on the instance store is lost; data that must be preserved should be on EBS.</Takeaway>

</Scene>
