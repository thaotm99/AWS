<Scene id="en-s1" label="Part 1/5" title="Retrieving data by key" questions={["exam4_q10", "exam2_q29", "exam3_q11", "exam6_q17", "exam4_q23", "exam6_q65"]}>

A **table** contains **items**; each item is a set of **attributes**, and items do not have to share the same structure. Each item has a **primary key**:

- **Partition key**: DynamoDB hashes this value to determine the partition that holds the item.
- **Sort key** (optional): orders the items that share a partition key, for example by order date.

Data is stored on SSDs and automatically replicated across multiple AZs in the Region. AWS describes DynamoDB as delivering single-digit millisecond performance at any scale, so queries by key do not slow down as the table grows. Try five ShopViet tasks:

<KeyAccessSim client:visible />

Some conclusions:

- To query by an attribute that is not a key: create a **GSI** (global secondary index) with any attribute as the new key; a GSI can be created at any time. An **LSI** shares the table's partition key, differs only in the sort key, and can be created only when the table is created.
- Large files (videos, images, a job's 20 MB output) are not stored in DynamoDB. The files are stored on S3 or EFS; DynamoDB stores only their path.
- Relational data that needs JOINs and has fluctuating load: Aurora Serverless v2 (RDS lesson), not DynamoDB.

<Takeaway>Retrieval by key, millisecond latency, serverless, automatic scaling: DynamoDB. Queries on other attributes: GSI. Items are at most 400 KB; large files go on S3. Access from a private subnet: a gateway endpoint (only S3 and DynamoDB support them).</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/5" title="Capacity modes, hot partitions and DAX" questions={["exam4_q62", "exam4_q54", "exam1_q1", "exam6_q6", "exam1_q29", "exam6_q47", "exam5_q65", "exam5_q37"]}>

DynamoDB measures read and write capacity in **RCUs** and **WCUs**. 1 RCU is one strongly consistent read per second (or two eventually consistent reads) for an item up to 4 KB. 1 WCU is one write per second for an item up to 1 KB. DynamoDB has two billing models:

- **Provisioned**: you provision RCUs/WCUs in advance and pay by the hour regardless of actual usage. Enable **Auto Scaling** so capacity follows the load, though Auto Scaling needs a few minutes to react.
- **On-Demand**: billed per request, with no forecasting needed. There are no read or write charges when there are no requests.

Each partition has its own limits: **3,000 RCUs** and **1,000 WCUs**. Choose a load pattern and a capacity mode, then simulate one day of operation:

<CapacitySim client:visible />

**DAX** (DynamoDB Accelerator) is an in-memory cache built for DynamoDB: it cuts latency from milliseconds to **microseconds**, uses the same API so almost no code changes are needed, and writes through to the table. DAX caches only **eventually consistent reads**; strongly consistent read requests go straight to the table. DAX fits when many users read the same data, for example when 90% of reads are concentrated on the home page and best-selling products. Static images on S3 are cached with CloudFront.

DynamoDB itself stores data on SSDs; it is **not** an in-memory database. When you need in-memory storage:

- Data on DynamoDB: DAX.
- Data on RDS or Aurora, or for a session store, leaderboards or location-based queries: **ElastiCache** (Analytics lesson). Multithreaded caching: Memcached. Sorted sets or geospatial: Valkey or Redis OSS.

<Takeaway>Fluctuating load that at times drops near zero: On-Demand. Steady, predictable load: Provisioned + Auto Scaling. A hot partition caused by repeated reads: DAX, not more RCUs. DAX is for DynamoDB; ElastiCache is for other data sources.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/5" title="Data flowing in and out" questions={["exam1_q33", "exam5_q32", "exam5_q35"]}>

When integrating DynamoDB with other components, ShopViet must answer three questions: how data gets in, how old data is deleted, and which component is notified when data changes.

<DataFlowSim client:visible />

- **TTL**: choose a Number attribute that holds the expiration time (Unix epoch, in seconds). DynamoDB automatically deletes expired items without consuming WCUs. Suits sessions, OTPs, abandoned carts and logs kept for N days.
- **DynamoDB Streams**: records every item-level change, in order, retained for 24 hours. Attach Lambda to process each change. Items deleted by TTL also appear in the stream as service deletions; Lambda reads that record (with OLD_IMAGE) to archive the item's contents to S3 after the item has been removed from the table. TTL typically deletes items within a few days after they expire.

<Takeaway>Deleting old data at no cost: TTL. Event-driven processing of data changes: Streams + Lambda. Sensitive data: sanitize it before writing. Getting data into DynamoDB with a serverless architecture: SQS → Lambda → DynamoDB; Firehose does not write to DynamoDB.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/5" title="Recovering from bad writes and accidental deletes" questions={["exam3_q49", "exam4_q42"]}>

The two most common data incidents come not from hardware but from human actions: a deploy that writes bad data, and an accidental delete. Choose the measure ShopViet put in place, then run the simulation:

<RecoverySim client:visible />

| | Use case | Restore point |
|---|---|---|
| **PITR** | Restore to the exact moment before an incident | Any second within 1–35 days, to a new table |
| **On-demand backup** | Long-term retention, compliance requirements | The exact moment the backup was created |
| **Deletion protection** | Prevent accidental deletes | Nothing to restore: the delete request is denied |
| **Export to S3** | Analytics with Athena, Glue, EMR; moving data to a bucket in another account or Region | Any point in time within the PITR window, written as DynamoDB JSON or Amazon Ion files in S3 |

**Export to S3** is a fully managed feature: it exports the whole table (full export) or the data changed during a time period (incremental export) from any point in time within the PITR window, so **the table must have PITR enabled**. Exports are asynchronous, **do not consume RCUs** and have no impact on table performance or availability; AWS does not guarantee completion times. It is a copy of the data for analytics, not a protection mechanism for the table: an export does not stop a table from being deleted, and reusing the data requires **import from S3**, which always creates a **new table**. If ShopViet only exported manually every week, a deleted table could lose up to a week of data, plus the time to import and switch the application to the new table.

<Takeaway>Restore to an exact point in time, down to the second: PITR. Prevent accidental deletes with the least operational overhead: deletion protection. Analyze table data with Athena without consuming RCUs: export to S3 (requires PITR). Streams, global tables and export to S3 do not replace deletion protection and PITR.</Takeaway>

</Scene>

<Scene id="en-s5" label="Part 5/5" title="Expanding to multiple Regions" questions={["exam5_q59", "exam5_q27", "exam2_q5", "exam1_q7"]}>

ShopViet expands into the European and US markets. The application is deployed in each Region; the problem to solve is how to organize the data.

<MultiRegionSim client:visible />

- **Global tables**: each Region has a replica, and every replica supports reads and writes. In the default mode (multi-Region eventual consistency, MREC), DynamoDB replicates asynchronously and automatically, usually within one second; multi-Region strong consistency (MRSC) mode is also available when you need strongly consistent reads across Regions. The application uses the DynamoDB API as before. For steady load, use Provisioned + Auto Scaling to optimize cost; note that writes to a global table are billed as replicated write units (rWCU/rWRU) in every Region that has a replica.
- **Aurora Global Database**: one Region accepts writes, with up to 10 read-only secondary Regions. Suits applications that already use SQL and JOINs and only need low-latency reads in other Regions. When only one table needs global reach and the other tables are needed only within the Region: split that table out; there is no need to move the whole database.

<Takeaway>Low-latency writes in multiple Regions: DynamoDB global tables. Keep a relational schema and only need reads in the Region near users: Aurora Global Database.</Takeaway>

</Scene>
