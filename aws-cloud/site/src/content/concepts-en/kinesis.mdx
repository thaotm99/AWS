The characteristics of **Kinesis Data Streams** shown in the simulation:

- A stream is divided into **shards**. The producer sends each record with a **partition key**; Kinesis hashes the key with MD5 to determine the shard. Records with the same key are written to the same shard, so one user's events always stay in order.
- Records are **not deleted** after being read. Each application (consumer) manages its own read position. Records are retained for 24 hours by default, extendable up to 365 days (with additional charges beyond 24 hours), so a failed application can reread the data.
- A consumer can be a self-developed application or **Lambda**: the Lambda event source mapping automatically polls each shard, reads records in batches and invokes the function with each batch. The ShopViet promotion leaderboard needs only a Kinesis → Lambda → DynamoDB architecture, with no servers to manage.
- **The number of parallel consumers is bounded by the shard count.** With the Kinesis Client Library (KCL), each shard is bound to only **one worker** at any given time by a *lease* (a worker can hold several leases); adding more workers than shards does not increase parallelism. With Lambda, the event source mapping processes the records in each shard in order; the `ParallelizationFactor` setting (1 by default, up to 10) allows up to 10 concurrent batches per shard, and Lambda still processes records in order at the partition-key level. To process faster, add shards.

ShopViet monitors 5,000 point-of-sale terminals in its stores, each sending data every minute. Each terminal's data must be processed in order, independently of the others, and the number of consumers must scale to roughly the number of terminals. Kinesis with the terminal ID as the partition key keeps the order, but the number of parallel consumers only equals the number of shards (far fewer than 5,000 terminals). An **SQS FIFO** queue with the terminal ID as the **message group ID** fits better: messages in the same group are always processed one at a time, in strict order, never two at once; different groups are read by several consumers simultaneously, so parallelism grows with the number of groups. If every message uses the same group ID, the whole queue is processed sequentially; an SQS standard queue does not guarantee order.

<Takeaway>Distributing tasks, each handled by one worker: SQS. Several applications reading one data stream, in order by key, with the ability to reread: Kinesis Data Streams. The partition key determines the shard; ordering is guaranteed only within one shard, and the number of parallel consumers is bounded by the shard count. Per-device ordering with consumers scaling to the number of devices: SQS FIFO with the device ID as the message group ID.</Takeaway>

Each shard has throughput limits: writes of **1,000 records or 1 MB per second**, reads of **2 MB per second** (total for all consumers using `GetRecords`). The simulation below shows three problems ShopViet ran into and the matching solutions. Run the simulation for 10 seconds, then turn on the fix:

<ShardThroughputSim client:visible />

A stream has two **capacity modes**. **Provisioned**: the operator sets the number of shards, and cost is per shard per hour; suited to predictable traffic. **On-demand**: Kinesis manages shards automatically, with no capacity planning, and cost is per GB of data written and read; suited to highly variable, unpredictable load. On-demand comes as **On-demand Standard** (each stream has an additional fixed charge) and **On-demand Advantage** (an account-level setting in a Region: no more fixed per-stream charge, warm throughput can be configured, a minimum data volume commitment is required). A new on-demand stream has a default write capacity of 4 MB/s and accommodates up to **double the peak write throughput of the previous 30 days**; if traffic grows to more than double the previous peak within 15 minutes, write requests can be throttled and must be retried.

<Takeaway>ProvisionedThroughput<wbr />ExceededException from sending each small record individually: aggregate records before sending, which costs less than adding shards. Unpredictable load: on-demand capacity mode (up to double the peak write throughput of the previous 30 days). Several consumers with growing read lag: enhanced fan-out, giving each consumer 2 MB/s per shard (up to 20 registered consumers per stream, 50 with On-demand Advantage).</Takeaway>

</Scene>

Two services that are often confused with Data Streams:

- **Amazon Data Firehose** (formerly Amazon Kinesis Data Firehose): **delivers data to destinations**, and can transform data before delivery. The documented destinations are Amazon S3, Apache Iceberg Tables, Amazon Redshift, Amazon OpenSearch Service, Amazon OpenSearch Serverless, Snowflake, Splunk, Splunk Observability Cloud, custom HTTP endpoints and the HTTP endpoints of supported third-party providers (Datadog, Dynatrace, New Relic, MongoDB Atlas, Sumo Logic, Elastic and others). **DynamoDB is not a Firehose destination**: to write sensor data into a DynamoDB table without provisioning capacity yourself, use SQS with Lambda reading in batches and writing to the table. No consumer to develop; the Firehose API has only write operations (`PutRecord`, `PutRecordBatch`), with no operation for applications to read or reread data.
- **Amazon Managed Service for Apache Flink** (formerly Amazon Kinesis Data Analytics for Apache Flink): processes streams **continuously** in Java, Scala, Python or SQL, for example counting clicks per minute; **Managed Service for Apache Flink Studio** lets you query streams interactively with SQL. The separate **Kinesis Data Analytics for SQL Applications** service has been discontinued: since 15 October 2025 no new applications can be created, and since 27 January 2026 applications are deleted; AWS recommends moving to Managed Service for Apache Flink or Flink Studio.

For applications already developed for **Apache Kafka**, use **Amazon MSK**: a fully managed Kafka service, and applications keep using the Kafka API. With MSK Serverless, MSK manages the brokers and the cluster capacity.

<Takeaway>Continuous stream analytics, including with SQL: Amazon Managed Service for Apache Flink (Kinesis Data Analytics for SQL Applications has been discontinued). Store a stream in S3 without writing code: Firehose (DynamoDB is not a destination). Full-text search: OpenSearch Service; dashboards: Amazon Quick Sight (formerly Amazon QuickSight). Move data from S3 into a stream: AWS DMS (full load of existing files; new changes must be CDC files in the DMS format). Jobs longer than 15 minutes: Fargate instead of Lambda. Systems already using Kafka: Amazon MSK.</Takeaway>
