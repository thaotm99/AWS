<p class="scene-intro">When the part that takes orders is faster than the part that processes them, a queue in between lets the first stop waiting while the second works through the backlog at its own pace.</p>

The flash sale starts at 20:00. The web tier takes orders at a high rate, while the processing tier (payment, stock deduction) has much lower throughput. The simulation below compares three ways to connect these two tiers:

<QueueBufferSim client:visible />

**Amazon SQS** is a queue service managed by AWS. The sender (producer) puts a message in the queue and continues with other work; the receiver (consumer) polls the queue to get messages and processes them at its own capacity. The high-throughput tier does not have to wait for the low-throughput tier; this model is called **decoupling**.

To scale a group of workers with the amount of work waiting in the queue, the Amazon EC2 Auto Scaling documentation recommends the **backlog per instance** metric: the number of messages available to retrieve from the queue (`ApproximateNumberOfMessages`, CloudWatch metric `ApproximateNumberOfMessagesVisible`) divided by the number of instances in the `InService` state, combined with **target tracking** to keep this metric near an acceptable value. A policy based only on the number of messages in the queue does not account for the number of instances already running, so it can add more instances than needed while the queue is already shrinking.

Some architectures that integrate a queue into the ShopViet system:

<Scene id="en-s2" label="Part 2/5" title="The life of a message" questions={["exam4_q46", "exam5_q44", "exam3_q34", "exam6_q37", "exam6_q32", "exam6_q16"]}>

<p class="scene-intro">A message in a queue is deleted only after it has been processed successfully; this ensures no work is lost when a worker fails midway.</p>

When a worker receives a message, the message is **not yet deleted** from the queue; it is only hidden for a period called the **visibility timeout**. After processing, the worker must call `DeleteMessage`. If the worker fails during processing, the message becomes visible again so that another worker can process it. SQS features all revolve around this life cycle. Choose each ShopViet scenario and run the simulation:

<MessageLifeSim client:visible />

Another pattern: the application sends a request to calculate shipping fees and **waits for the response** (request-response). Creating a real queue for each request costs time and money. A **temporary queue** (through the Temporary Queue Client) creates virtual queues inside the application, multiplexes them onto one real SQS queue and cleans them up automatically when done.

A delay queue applies to every message in the queue. When only some messages need a delay (for example a payment reminder email sent after 10 minutes), the producer sets a **message timer**: the `DelaySeconds` parameter on an individual message when it is sent, from 0 seconds (the default) up to a maximum of 15 minutes; this value overrides the delay queue's `DelaySeconds`. FIFO queues don't support timers on individual messages. For scheduling further than 15 minutes ahead, AWS recommends **EventBridge Scheduler**. Message timers, delay queues and the visibility timeout only decide **when** a message is visible; none of them is a way to receive messages, and none of them reduces the number of `ReceiveMessage` calls that return empty. Only **long polling** (maximum wait time 20 seconds) reduces empty responses and therefore cost.

<Takeaway>Visibility timeout: hide a message while it is being processed (default 30 seconds, maximum 12 hours). Dead-letter queue: isolate messages that fail processing repeatedly. Long polling: fewer empty receives and lower cost. Delay queue: postpone every new message sent to the queue; message timer: postpone an individual message (0 to 15 minutes, not supported on FIFO queues). Processing priority: two queues, read the high-priority queue first. Request-response: temporary queues.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/5" title="Guaranteed ordering and exactly-once processing: FIFO queues" questions={["exam1_q13", "exam1_q34", "exam3_q2", "exam2_q42"]}>

<p class="scene-intro">For money transactions, order and exactly-once processing are mandatory; the default queue does not guarantee them, so another queue type is needed.</p>

The default queue type is **standard**: very high throughput, but a message can be delivered **more than once** and **ordering is not guaranteed**. For orders, the worker can check for duplicates itself. For ShopViet's e-wallet this is not acceptable: a top-up must be processed before a payment, and each command must be processed exactly once. The simulation below compares three options:

<FifoSim client:visible />

A **FIFO queue** guarantees ordering and removes duplicate messages (by deduplication ID within a 5-minute interval). In exchange, throughput is limited. Without high throughput mode, a FIFO queue supports **300 transactions per second per API action** (`SendMessage`, `ReceiveMessage`, `DeleteMessage`); with batches of up to 10 messages per call, throughput reaches **3,000 messages per second** per API action. Adjust the values to check:

<FifoBatchCalc client:visible />

An existing standard queue cannot be converted to FIFO. You must **create a new FIFO queue** whose name ends in `.fifo`, then move the producers and consumers to the new queue.

Sending wallet commands through **EventBridge** does not meet the requirement either. On an event bus (the classic type), EventBridge delivers to targets **at least once**: the EventBridge documentation notes that in rare cases the same rule can run more than once for a single event, or the same target can be invoked more than once; events are delivered to targets in an arbitrary order. When delivery fails, EventBridge by default retries for 24 hours and up to 185 times, then drops the event unless a dead-letter queue is configured. EventBridge also does not keep events for the processing tier to pull at its own pace the way a queue does. Since September 2026, the **enhanced custom event bus** adds ordered delivery for events that share an `EventGroupId` and optional content-based deduplication that drops publisher retries within five minutes; these are features of the new bus type and do not change the at-least-once behavior of the classic event bus.

<Takeaway>Ordering and no duplicates required: FIFO queue (name ends in .fifo, must be created new, cannot be converted from standard). Standard queues and EventBridge (classic event bus) both deliver at least once without guaranteed ordering. Parallel processing while keeping order within each group: Message Group ID. Without high throughput mode: 300 calls/s per API action; with batches of 10 messages: 3,000 messages/s.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/5" title="Distributing events to multiple targets and orchestrating multi-step workflows" questions={["exam4_q35", "exam3_q30", "exam2_q27", "exam6_q55", "exam1_q15", "exam4_q51", "exam6_q61", "exam2_q1", "exam2_q9", "exam1_q61", "exam1_q50", "exam5_q17"]}>

<p class="scene-intro">Not all communication is one sender and one receiver; some events must reach many places, some tasks run on a schedule, and some processes have several steps in sequence.</p>

A queue follows a one-sender, one-receiver model. ShopViet has other needs too: one event must notify several components, events come from external software, jobs run on a schedule, workflows have several steps, or a legacy application uses its own protocol. Choose a scenario and change the setting to compare:

<EventRouterSim client:visible />

Some problems ShopViet ran into in real operation:

- **SNS invokes Lambda** to send notifications: during the sales season, when sending volume grew 50-fold, some notifications were not delivered. The cause was not SNS but Lambda reaching the account's **concurrency quota** in the Region. The solution is to request a quota increase (see the Lambda lesson).
- Detecting mass unauthorized API calls: send CloudTrail logs to CloudWatch Logs, create a **metric filter** that counts the error codes, set an **alarm** on that metric, and configure the alarm to notify the security team's **SNS topic**.
- SNS topics and SQS queues both have resource policies. To identify which resources allow access from external accounts, **IAM Access Analyzer** analyzes these policies and reports its findings.
- An audit report run by Step Functions reads its data only twice a year but needs immediate retrieval: store the data in a storage class for infrequently accessed data. **S3 Standard-IA** is designed for data accessed about once a month; **S3 Glacier Instant Retrieval** is for data accessed about once a quarter. Both retrieve in milliseconds, have a designed availability of 99.9% and charge a per-GB retrieval fee; their minimum storage durations are 30 days and 90 days respectively.

<Takeaway>One event, many receivers: SNS fan-out to multiple SQS queues. Events from SaaS or AWS services, filtered by content: EventBridge. Scheduled jobs: EventBridge (Lambda for short jobs, Fargate for long jobs). Multi-step workflows with retries: Step Functions. Legacy applications using an ActiveMQ or RabbitMQ broker and the AMQP, MQTT or STOMP protocols: Amazon MQ.</Takeaway>

</Scene>
