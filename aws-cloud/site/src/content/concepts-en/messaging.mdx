In its early days, ShopViet's web application called every component synchronously: after creating an order, the application called the payment service, the inventory service and the email service in turn and waited for each response. <QueueBufferSim client:visible />

**Amazon SQS** is a queue service managed by AWS. The sender (producer) puts a message in the queue and continues with other work; the receiver (consumer) polls the queue to get messages and processes them at its own capacity. The high-throughput tier does not have to wait for the low-throughput tier; this model is called **decoupling**.

To scale a group of workers with the amount of work waiting in the queue, the Amazon EC2 Auto Scaling documentation recommends the **backlog per instance** metric: the number of messages available to retrieve from the queue (`ApproximateNumberOfMessages`, CloudWatch metric `ApproximateNumberOfMessagesVisible`) divided by the number of instances in the `InService` state, combined with **target tracking** to keep this metric near an acceptable value. A policy based only on the number of messages in the queue does not account for the number of instances already running, so it can add more instances than needed while the queue is already shrinking.

<Scene id="en-s2" label="Part 2/4" title="The life of a message" questions={["exam4_q46", "exam5_q44", "exam3_q34", "exam6_q37", "exam6_q32", "exam6_q16"]}>

When a worker receives a message, the message is **not yet deleted** from the queue; it is only hidden for a period called the **visibility timeout**. After processing, the worker must call `DeleteMessage`. If the worker fails during processing, the message becomes visible again so that another worker can process it. SQS features all revolve around this life cycle. Choose each ShopViet scenario and run the simulation:

<MessageLifeSim client:visible />

Another pattern: the application sends a request to calculate shipping fees and **waits for the response** (request-response). Creating a real queue for each request costs time and money. A **temporary queue** (through the Temporary Queue Client) creates virtual queues inside the application, multiplexes them onto one real SQS queue and cleans them up automatically when done.

<Takeaway>Visibility timeout: hide a message while it is being processed. Dead-letter queue: isolate messages that fail processing repeatedly. Long polling: fewer empty receives and lower cost. Delay queue: postpone the delivery of newly sent messages. Processing priority: two queues, read the high-priority queue first. Request-response: temporary queues.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/4" title="Guaranteed ordering and exactly-once processing: FIFO queues" questions={["exam1_q13", "exam1_q34", "exam3_q2", "exam2_q42"]}>

The default queue type is **standard**: very high throughput, but a message can be delivered **more than once** and **ordering is not guaranteed**. For orders, the worker can check for duplicates itself. For ShopViet's e-wallet this is not acceptable: a top-up must be processed before a payment, and each command must be processed exactly once. The simulation below compares three options:

<FifoSim client:visible />

A **FIFO queue** guarantees ordering and removes duplicate messages (by deduplication ID within a 5-minute interval). In exchange, throughput is limited. Without high throughput mode, a FIFO queue supports **300 transactions per second per API action** (`SendMessage`, `ReceiveMessage`, `DeleteMessage`); with batches of up to 10 messages per call, throughput reaches **3,000 messages per second** per API action. Adjust the values to check:

<FifoBatchCalc client:visible />

An existing standard queue cannot be converted to FIFO. You must **create a new FIFO queue** whose name ends in `.fifo`, then move the producers and consumers to the new queue.

<Takeaway>Ordering and no duplicates required: FIFO queue (name ends in .fifo, must be created new, cannot be converted from standard). Parallel processing while keeping order within each group: Message Group ID. Without high throughput mode: 300 calls/s per API action; with batches of 10 messages: 3,000 messages/s.</Takeaway>

</Scene>

Some problems ShopViet ran into in real operation:

- **SNS invokes Lambda** to send notifications: during the sales season, when sending volume grew 50-fold, some notifications were not delivered. The cause was not SNS but Lambda reaching the account's **concurrency quota** in the Region. The solution is to request a quota increase (see the Lambda lesson).
- Detecting mass unauthorized API calls: send CloudTrail logs to CloudWatch Logs, create a **metric filter** that counts the error codes, set an **alarm** on that metric, and configure the alarm to notify the security team's **SNS topic**.
- SNS topics and SQS queues both have resource policies. To identify which resources allow access from external accounts, **IAM Access Analyzer** analyzes these policies and reports its findings.
- An audit report run by Step Functions reads its data only twice a year but needs immediate retrieval: store the data in a storage class for infrequently accessed data. **S3 Standard-IA** is designed for data accessed about once a month; **S3 Glacier Instant Retrieval** is for data accessed about once a quarter. Both retrieve in milliseconds, have a designed availability of 99.9% and charge a per-GB retrieval fee; their minimum storage durations are 30 days and 90 days respectively.

<Takeaway>One event, many receivers: SNS fan-out to multiple SQS queues. Events from SaaS or AWS services, filtered by content: EventBridge. Scheduled jobs: EventBridge (Lambda for short jobs, Fargate for long jobs). Multi-step workflows with retries: Step Functions. Legacy applications using an ActiveMQ or RabbitMQ broker and the AMQP, MQTT or STOMP protocols: Amazon MQ.</Takeaway>

</Scene>
