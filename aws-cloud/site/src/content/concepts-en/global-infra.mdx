<Scene id="en-s1" label="Part 1/7" title="Region scope: resources are not automatically available in another Region" questions={["exam1_q41", "exam4_q5"]}>

A **Region** is an independent geographic area, for example Singapore or Tokyo. Many resources, such as **AMIs** and **EBS snapshots**, exist only in the Region where they were created. ShopViet needs to prepare a recovery plan in Tokyo. Perform each step in turn, or try launching directly in Tokyo to see the result.

<AmiCopySim client:visible />

<Takeaway>AMIs and snapshots are Regional resources. To use them in another Region, they must be copied; when you copy an AMI, AWS automatically creates the corresponding snapshot in the destination Region. For fast recovery in another Region, the AMI must be copied to that Region in advance.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/7" title="The scope of each resource type" questions={["exam1_q42", "exam3_q62"]}>

A Region consists of multiple **Availability Zones (AZs)**: data centers with independent power and networking, connected to each other by a private low-latency network. The scope of a resource determines its fault tolerance. Select each ShopViet resource to see its scope.

<ScopeExplorer client:visible />

<Takeaway>Regional resources (S3, EFS, AMI, VPC) can be used from every AZ. AZ-scoped resources (subnet, EC2, EBS, NAT gateway in zonal mode) are tied to one AZ; to tolerate an AZ failure, these resources must be created in multiple AZs. A NAT gateway in regional mode automatically expands to the AZs that have workloads.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/7" title="Edge locations: CloudFront caches content, S3 Transfer Acceleration speeds transfers to and from a bucket" questions={["exam1_q62", "exam6_q5", "exam6_q58", "exam1_q18", "exam3_q37"]}>

**Edge locations** are AWS points of presence located close to users, far more numerous than Regions. **CloudFront** caches content at these locations; the origin can be S3, an ALB or an on-premises server. ShopViet's product images are stored in S3 in Singapore. Fetch an image twice to compare the results.

<EdgeCacheDemo client:visible />

**S3 Transfer Acceleration** also uses edge locations, but not to cache content: data enters the edge location close to the client, then travels over an optimized AWS network path to the bucket. According to the S3 FAQs, Transfer Acceleration speeds up long-distance transfers **to and from** a single bucket, meaning both uploads (PUT) and downloads (GET), and helps most with larger objects. When suppliers on several continents both upload and download videos of up to 10 GB from the Singapore bucket, enabling Transfer Acceleration alone improves both directions; large uploads are usually combined with **multipart upload**. AWS suggests considering CloudFront's PUT/POST when objects or the data set are smaller than 1 GB; for larger files, Transfer Acceleration gives higher throughput.

<Takeaway>Many distant users repeatedly fetching the same content: CloudFront caches it at edge locations (even when the backend must stay where it is). Large files (about 1 GB and up) moved over long distances to or from an S3 bucket, uploads and downloads alike: S3 Transfer Acceleration (combine uploads with multipart upload). Files under 1 GB: consider CloudFront PUT/POST.</Takeaway>

</Scene>

<Scene id="en-s5" label="Part 5/7" title="Global Accelerator: static IP addresses, TCP/UDP and failover between Regions" questions={["exam1_q59", "exam2_q7", "exam2_q22", "exam3_q8", "exam3_q45", "exam4_q58", "exam5_q4", "exam5_q30", "exam5_q55", "exam1_q62", "exam6_q5", "exam6_q58", "exam1_q18", "exam3_q37"]}>

**AWS Global Accelerator** also uses edge locations but does not cache content. The service provides **2 static anycast IPv4 addresses** (dual-stack: 2 additional IPv6 addresses), receives TCP/UDP traffic at the edge location closest to the user, then carries it over the AWS private network to the nearest healthy endpoint (ALB, NLB, EC2 or Elastic IP) in one or more Regions. The simulation below compares it with a DNS-only approach when a Region fails:

<GlobalAcceleratorSim client:visible />

The three services all use edge locations but solve three different problems. Choose a ShopViet scenario, apply each service in turn and press **Send traffic** to find the service that meets the requirement.

<EdgeChoiceSim client:visible />

<Takeaway>UDP, static IP addresses for partners to put in an allow list, or Region failover that does not depend on DNS: Global Accelerator. Caching pages, images, video: CloudFront. Uploading large files to S3: S3 Transfer Acceleration.</Takeaway>

</Scene>

<Scene id="en-bluegreen" label="Part 6/7" title="Global blue/green: shift traffic with endpoint weights instead of DNS" questions={["exam2_q22"]}>

Two days before a major sale, ShopViet needs to test a new version (green) of its global application on as many users as possible, while most users connect from mobile phones. The current version (blue) and green run side by side. There are two ways to send part of the traffic to green:

- **Route 53 weighted routing**: Route 53 answers DNS queries according to the weights of the records. A change reaches a device only when the DNS answer cached by the device or its resolver expires; some devices and resolvers cache answers for long periods, so there is no way to know when every user gets the new address.
- **Global Accelerator**: users always connect to 2 static anycast IP addresses. The **endpoint weight** (0–255, default 128) sets the proportion of traffic between the endpoints in an endpoint group; a weight of 0 stops traffic to that endpoint. The **traffic dial** (0–100%, default 100%) sets the percentage of traffic to a whole endpoint group (one Region) and applies only to new connections. Weight and traffic dial changes take effect within seconds, independent of DNS caching.

Choose a mechanism, set the share sent to green and apply the change. The cache time of each phone in the simulation is only an illustration.

<BlueGreenSim client:visible />

<Takeaway>Blue/green for a global application whose mobile users are affected by DNS caching, with a fast and controlled traffic shift: Global Accelerator with endpoint weights (between endpoints) and traffic dials (between Regions). Route 53 weighted routing fits when the delay caused by DNS caching is acceptable. CodeDeploy deploys code; it does not distribute traffic between environments.</Takeaway>

</Scene>

<Takeaway>A Read Replica in the same Region has no replication charge; a Read Replica in another Region does. <Scene id="en-deep" label="Going further" title="Data that must stay on premises: Outposts and infrastructure close to users" questions={["exam1_q27"]}>

ShopViet's payment subsidiary runs Kubernetes in its own data center. Regulations require all data and workloads to stay physically in that data center, but the infrastructure team wants an AWS-managed Kubernetes control plane, CloudWatch and IAM.

**AWS Outposts** is a fully managed service that extends AWS infrastructure, services, APIs and tools to customer premises; AWS operates, monitors and manages the Outpost capacity as part of a Region. **Amazon EKS on Outposts** has two options: *extended clusters* (control plane in the Region, nodes on the Outpost) and *local clusters* (control plane and nodes on the Outpost); with both, the control plane is fully managed by AWS. AWS recommends local clusters when Kubernetes operations must continue through network disconnects from the Region or when data residency mandates require it.

The services below also bring resources close to users or on premises, but they do not meet this requirement. Select each one to compare.
