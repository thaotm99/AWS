At night ShopViet needs only 2 instances; on Friday evening, during a sale, it needs 12. Running 12 instances all day wastes money, while running only 2 increases latency for users. An **Auto Scaling group** (ASG) automatically adjusts the number of EC2 instances to the load. The designer needs to configure when to scale out, the minimum capacity, and which instance is removed on scale in.

<Scene id="en-s1" label="Part 1/4" title="A scaling policy for each load pattern" questions={["exam1_q30", "exam3_q54", "exam6_q52", "exam1_q45", "exam4_q21", "exam3_q15", "exam4_q56", "exam4_q53"]}>

The ShopViet website has dynamic content that changes constantly and a cache cannot absorb all the load, so instances must be added when traffic rises. However, when to scale out depends on the load pattern. Pick a day of ShopViet operations, choose a scaling policy, then run the simulation for the whole day to find the hours when users have to wait:

<ScalingPolicySim client:visible />

Containers scale in a similar way. When an ECS service is CPU-bound, turn on **Service Auto Scaling** to increase the number of tasks. When pods on EKS are pending because the cluster is out of resources, **Cluster Autoscaler** adjusts the desired capacity of the EC2 Auto Scaling group to add nodes (Karpenter is another option described in the EKS documentation).

<Takeaway>Keep a metric at a steady level: target tracking. Queue workers: target tracking on SQS backlog per instance. Peak hours known in advance: scheduled action. Cyclical load: predictive scaling combined with target tracking to handle unusual fluctuations.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/4" title="How many instances to tolerate an AZ failure" questions={["exam2_q31", "exam5_q61"]}>

ShopViet must keep at least N instances running, even when one AZ fails. Adjust N, choose the number of AZs, then press "Simulate AZ 1 failure" to check.

<AzCapacityCalc client:visible />

Two common cases. A minimum of 4 instances: 3 AZs × 2 = 6 is the lowest-cost option, because with 2 AZs × 2 = 4, only 2 instances remain after losing an AZ. A minimum of 2 instances but only 2 AZs available: set minimum = 4, with 2 instances in each AZ.

<Takeaway>Each AZ needs ⌈N ÷ (number of AZs − 1)⌉ instances. When the system must tolerate the failure of one AZ, spreading across more AZs usually costs less.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/4" title="Scale in: the order in which instances are terminated" questions={["exam4_q16", "exam2_q65", "exam1_q54"]}>

After the sale, the ASG scales in. With the default termination policy, the ASG evaluates in a fixed order. Pick a scenario, predict which instance will be terminated, then follow each step.

<TerminationSim client:visible />

<Takeaway>Default order: the AZ with the most instances → instances with an outdated configuration (launch configuration first, then a launch template other than the current one, then the oldest version of the current template) → if several instances remain: the one closest to the next billing hour (AWS notes this criterion has little effect because most EC2 usage is billed per second). The ASG also automatically rebalances across AZs and replaces unhealthy instances.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/4" title="Maintaining instances without the ASG replacing them" questions={["exam1_q32", "exam5_q1", "exam2_q18", "exam4_q49"]}>

The ASG replaces every instance it determines to be unhealthy. That works when an instance has really failed, but causes problems when an instance is being patched or a new instance has not finished starting. The ELB lesson explained that the ASG needs to use **ELB health checks** to follow the load balancer's results; in this part the ASG is using ELB health checks. Try three maintenance tasks:

<MaintenanceSim client:visible />

On cost: ShopViet always needs at least 2 instances, more at peak hours. Set minimum = 2 and buy **Reserved Instances** for the 2 instances that run continuously; the extra capacity is paid On-Demand.

<Takeaway>Patching an instance: move it to Standby, or suspend ReplaceUnhealthy and then resume it. A new instance needs time to install the application: configure a health check grace period. The ASG replaces instances the load balancer marks as failed: ELB health checks.</Takeaway>

</Scene>
