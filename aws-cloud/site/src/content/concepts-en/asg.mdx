<Scene id="en-setup" label="Part 1/7" title="Auto Scaling group configuration: launch template, subnets and capacity" questions={["exam5_q36", "exam2_q33", "exam5_q61", "exam1_q45", "exam3_q45"]}>

<p class="scene-intro">Instead of running a fixed number of EC2 instances, an Auto Scaling group launches instances as load rises and terminates them as it falls; to do that, the group needs a launch template that describes how to launch a new instance.</p>

ShopViet's reporting application used to run on a single On-Demand EC2 instance, and every load spike caused 5xx errors. To move it to an Auto Scaling group, the operations team creates an AMI from the current instance, declares that AMI in a **launch template**, then chooses the subnets and purchase options for the group. Try each choice below:

<GroupSetupSim client:visible />

Three points matter. First, a **launch template** describes how to launch an instance (AMI, instance type, key pair, security groups…) and has multiple versions; a launch configuration is the legacy mechanism, cannot be modified after creation and does not support combining On-Demand and Spot or multiple instance types. Second, an ASG is a regional construct: it can span Availability Zones but **cannot span AWS Regions**; a multi-Region architecture needs one ASG in each Region. Third, a **mixed instances policy** lets one ASG run both On-Demand and Spot: an On-Demand base for the steady load, and capacity above the base split by percentage. When the steady load stays at a known level all year, buy Reserved Instances (or a Savings Plan) for it; do not use Spot for the baseline, because EC2 can reclaim a Spot Instance when capacity is no longer available.

A payment partner asks ShopViet for fixed IP addresses to add to its firewall. **An Elastic IP address cannot be assigned to an Auto Scaling group**: an Elastic IP address is associated with an instance or a network interface, while an ASG is only a group that manages instances that are constantly launched and replaced. If each instance really must have an Elastic IP address, you associate it yourself at launch (for example a user data script or a launch lifecycle hook that calls the AssociateAddress API). The more common approach is a static IP in front: an internet-facing **NLB** lets you select one Elastic IP address per AZ, or **AWS Global Accelerator** provides static IP addresses across Regions ([ELB lesson, part 1](/concepts/elb/alb-or-nlb/)).

Three values decide the group's size. **Desired capacity** is the number of instances the ASG tries to maintain; **minimum** and **maximum** are limits that scaling policies and scheduled actions cannot cross. The accounting team needs exactly 10 instances during the month-end payroll hour:

<CapacityRangeSim client:visible />

<Takeaway>Launch template: defines the instance, is versioned, and is required to combine On-Demand and Spot. An ASG spans multiple AZs in one Region, never across Regions. A specific number of instances at a specific time: a scheduled action sets desired capacity; min/max are only the limits of the scaling range. Fixed baseline load: Reserved Instances; the variable part: On-Demand and Spot through a mixed instances policy. An Elastic IP address attaches to an instance or network interface, never to an ASG; static IPs for the whole group: an NLB with Elastic IPs or Global Accelerator.</Takeaway>

</Scene>

<Scene id="en-s1" label="Part 2/7" title="Scaling policies for each load pattern" questions={["exam1_q30", "exam3_q54", "exam6_q52", "exam1_q45", "exam4_q21", "exam3_q15", "exam4_q56", "exam4_q53"]}>

<p class="scene-intro">Website load changes by hour, by day and with events; the scaling policy must match that load pattern so capacity is neither too low nor too high.</p>

The ShopViet website has dynamic content that changes constantly and a cache cannot absorb all the load, so instances must be added when traffic rises. However, when to scale out depends on the load pattern. Pick a day of ShopViet operations, choose a scaling policy, then run the simulation for the whole day to find the hours when users have to wait:

<ScalingPolicySim client:visible />

Containers scale in a similar way. When an ECS service is CPU-bound, turn on **Service Auto Scaling** to increase the number of tasks. When pods on EKS are in the Pending state because the cluster is out of resources, **Cluster Autoscaler** adjusts the desired capacity of the EC2 Auto Scaling group to add nodes (Karpenter is another option described in the EKS documentation).

<Takeaway>Keep a metric at a steady level: target tracking. Queue workers: target tracking on SQS backlog per instance. Peak hours known in advance: scheduled action. Cyclical load: predictive scaling combined with target tracking to handle unusual fluctuations.</Takeaway>

</Scene>

<Scene id="en-dynamic" label="Part 3/7" title="Dynamic scaling: simple, step and target tracking scaling policies" questions={["exam1_q30", "exam3_q54", "exam4_q21"]}>

<p class="scene-intro">When load spikes, what matters is how many instances to launch and how fast; each type of dynamic scaling policy handles this differently.</p>

All three dynamic scaling policies react to a CloudWatch metric, but they differ in how they calculate the instances to add and when they may react again. With simple and step scaling, the designer creates CloudWatch alarms with fixed thresholds; with target tracking, the designer only picks a metric and a target value, and Auto Scaling creates and manages the alarms. Run the same surge under each policy:

<DynamicPolicySim client:visible />

Two time settings are easy to confuse. The **cooldown** (300 seconds by default) applies to simple scaling: after each scaling activity, the policy does not respond to new alarms until the cooldown ends. **Instance warmup** applies to target tracking and step scaling: a new instance does not count toward the group's aggregated metrics until its warmup ends, but it already counts toward desired capacity, so the policy does not launch extra instances. AWS recommends enabling the **default instance warmup** for the group.

<Takeaway>Keep a metric near a value (CPU 50%, SQS backlog per instance): target tracking, not step or simple. Step scaling: the adjustment depends on the size of the breach and alarms keep being answered. Simple scaling: one adjustment, then wait for the activity and the cooldown, so it reacts slowly to a sudden surge; AWS recommends against it. All three react after load rises; cyclical load needs predictive scaling.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 4/7" title="Distributing capacity across Availability Zones" questions={["exam2_q31", "exam5_q61"]}>

<p class="scene-intro">To keep enough capacity when an AZ fails, the instance count must be planned so the remaining AZs can carry the whole load on their own.</p>

ShopViet must keep at least N instances running, even when one AZ fails. Adjust N, choose the number of AZs, then press "Simulate AZ 1 failure" to check.

<AzCapacityCalc client:visible />

Two common cases. A minimum of 4 instances: 3 AZs × 2 = 6 is the lowest-cost option, because with 2 AZs × 2 = 4, only 2 instances remain after losing an AZ. A minimum of 2 instances but only 2 AZs available: set minimum = 4, with 2 instances in each AZ.

<Takeaway>Each AZ needs ⌈N ÷ (number of AZs − 1)⌉ instances. When the system must tolerate the failure of one AZ, spreading across more AZs usually costs less.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 5/7" title="Termination policies for scale in" questions={["exam4_q16", "exam2_q65", "exam1_q54", "exam5_q33"]}>

<p class="scene-intro">When load falls, the Auto Scaling group scales in; the instance terminated first is chosen in a fixed, predictable order.</p>

After the sale, the ASG scales in. With the default termination policy, the ASG evaluates in a fixed order. Pick a scenario, predict which instance will be terminated, then follow each step.

<TerminationSim client:visible />

The second scenario adds a choice of how the group is configured. In a group that uses a **launch template**, every instance still running from a launch configuration counts as outdated and is considered first (B and C), and only then the billing-hour criterion applies. In a group that uses a **launch configuration**, the ASG picks the instances with the **oldest launch configuration** (B). Launch configurations are legacy: since January 1, 2023 they do not support new instance types, accounts created on or after October 1, 2024 cannot create new launch configurations by any method, and AWS recommends migrating to launch templates.

The third scenario uses **instance scale-in protection**: a protected instance is not selected on scale in. It can be enabled for the whole group (new instances inherit the setting) or for individual instances. Scale-in protection does **not** protect an instance from health check replacement, Spot interruptions or manual termination. When engineers need the logs of an instance that was scaled in, the durable solution is to ship logs to CloudWatch Logs with the CloudWatch agent (Monitoring lesson), not to keep the instance around.

<Takeaway>Default order: the AZ with the most instances → instances with an outdated configuration (group with a launch template: launch configuration first, then a launch template other than the current one, then the oldest version of the current template; group with a launch configuration: the oldest launch configuration) → if several instances remain: the one closest to the next billing hour (AWS notes this criterion has little effect because most EC2 usage is billed per second). The ASG also automatically rebalances across AZs and replaces unhealthy instances.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 6/7" title="Instance maintenance: Standby, suspended processes and health check grace period" questions={["exam1_q32", "exam5_q1", "exam2_q18", "exam4_q49"]}>

<p class="scene-intro">Automatically replacing unhealthy instances keeps capacity up, but it can also replace an instance that is under maintenance or still starting up; you need a way to pause it at the right moments.</p>

The ASG replaces every instance it determines to be unhealthy. That works when an instance has really failed, but causes problems when an instance is being patched or a new instance has not finished starting. The ELB lesson explained that the ASG needs to use **ELB health checks** to follow the load balancer's results; in this part the ASG is using ELB health checks. Try three maintenance tasks:

<MaintenanceSim client:visible />

On cost: ShopViet always needs at least 2 instances, more at peak hours. Set minimum = 2 and buy **Reserved Instances** for the 2 instances that run continuously; the extra capacity is paid On-Demand.

<Takeaway>Patching an instance: move it to Standby, or suspend ReplaceUnhealthy and then resume it. A new instance needs time to install the application: configure a health check grace period. The ASG replaces instances the load balancer marks as unhealthy: ELB health checks.</Takeaway>

</Scene>

<Scene id="en-health" label="Part 7/7" title="Health checks and replacement of unhealthy instances" questions={["exam2_q18", "exam1_q54"]}>

<p class="scene-intro">Whether a failing instance is replaced, and when, depends on which health check detects the failure and which scaling activity the Auto Scaling group is performing.</p>

A ShopViet instance shows signs of failure but the ASG has not replaced it, or replaces it in a different order than expected. The outcome depends on which health check detects the failure and which kind of activity the ASG performs. Run each situation, then switch the option to compare:

<HealthReplaceSim client:visible />

When the ASG has not terminated a failed instance, check in turn: the instance is still within its health check grace period; the status check is impaired and the ASG is waiting a few minutes; the group's health check type is EC2, so ELB results are ignored. Raising the minimum capacity does not keep an unhealthy instance alive, and Spot Instances in the group are also replaced when unhealthy.

<Takeaway>Impaired status check: the ASG waits a few minutes before marking the instance Unhealthy; an instance no longer running is replaced immediately. ELB health checks only count when turned on for the ASG. A custom health check that calls SetInstanceHealth makes the ASG replace the instance (respecting the grace period by default). Health check replacement: terminate first, then launch (changeable with an instance maintenance policy). AZ rebalancing: launch first, then terminate.</Takeaway>

</Scene>
