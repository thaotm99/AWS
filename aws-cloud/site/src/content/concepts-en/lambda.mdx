<Scene id="en-s2" label="Part 2/4" title="Running Lambda functions in production" questions={["exam4_q25", "exam1_q50", "exam3_q20", "exam6_q35", "exam4_q39", "exam2_q16"]}>

<p class="scene-intro">A function that works in testing can still run into problems in production: networking after VPC attachment, cold starts, concurrency quotas and how credentials are stored.</p>

Some problems appear only after deploying to production: a function attached to a VPC cannot reach the internet, latency rises at peak hours because of cold starts, notifications are throttled when the concurrency quota is exceeded, the database password is stored in configuration. Pick each scenario, try it, then turn on the option to fix it:

<LambdaRunSim client:visible />

Two more notes. Each invocation of a standard Lambda function runs at most **15 minutes** (900 seconds; Lambda Managed Instances allows up to 90 minutes for asynchronous invocations or through an event source mapping, except Amazon MQ and Amazon DocumentDB); longer jobs should run as containers on Fargate (Containers lesson). A Lambda function that is not attached to a VPC can already reach the internet and public AWS APIs; attach it to a VPC only when it needs private resources such as RDS, and then it needs a NAT gateway as in the simulation above. Sizing memory, /tmp and the timeout, and packaging (layers, container images), are covered in part 3.

<Takeaway>Lambda in a VPC needs a NAT gateway to reach the internet. Cold starts at peak hours: provisioned concurrency. Concurrency has a quota per account and Region; configure an alarm on ConcurrentExecutions. Do not store passwords: IAM database authentication. Cross-account access: both the execution role and the bucket policy must allow it.</Takeaway>

<Scene id="en-sizing" label="Part 3/4" title="Configuring memory, ephemeral storage, timeout and function packaging" questions={["exam4_q25", "exam3_q32", "exam1_q9"]}>

<p class="scene-intro">Each function gets a fixed amount of resources for every invocation; configuring those resources correctly directly affects performance and cost.</p>

A few settings of each Lambda function decide the resources of its execution environment:

- **Memory** from 128 MB (the default) to 10,240 MB. Lambda has no separate CPU setting: CPU is allocated **in proportion to memory**, and at 1,769 MB a function has the equivalent of one vCPU. A CPU-bound task that runs slowly needs more memory. Duration is billed in GB-seconds, so its cost depends on the memory allocated.
- **Ephemeral storage** (`/tmp`) from 512 MB (the default) to 10,240 MB, encrypted at rest with an AWS managed key. Data in `/tmp` is **unique to each execution environment** and is only a transient cache: it can remain when the environment is reused, but Lambda terminates environments every few hours. Data that must last or be shared between functions belongs in Amazon S3 or Amazon EFS.
- **Timeout**, 3 seconds by default and at most 900 seconds. A timeout close to the run time fails when the data is larger than usual; a timeout set far too high lets a hung invocation hold its execution environment longer than needed. Load testing finds the right value.
- **Package type**: a .zip file archive (at most 250 MB unzipped, **including layers**) or a **container image** stored in Amazon ECR in the same Region (up to 10 GB). A **Lambda layer** holds libraries, a custom runtime or configuration files shared by several functions; a function uses up to 5 layers, each layer version is an immutable snapshot, and layers apply only to .zip functions.

Initialization time (the cold start) depends on the package size, including libraries, dependencies and layers. Moving a library into a layer keeps the package small and shareable, but does not remove the library's initialization time; to reduce cold starts, import only what the function needs, or use provisioned concurrency (part 2).

A layer is not a place to keep data. When the recommendations team needs to read a large, growing dataset on EFS in a partner's account, Lambda mounts that EFS file system directly through an access point, with a file system policy that allows cross-account access and VPC peering for connectivity: see the [Storage lesson, part 3](/concepts/storage/efs-configuration/). Packaging data into a layer does not fit, because layer versions are immutable and share the 250 MB limit with the package.

<Takeaway>CPU is proportional to memory (1,769 MB ≈ 1 vCPU). `/tmp` is 512 MB to 10,240 MB, temporary and unique to each execution environment; durable data goes to S3 or EFS. Set the timeout from load tests, not with a large margin. A .zip package is at most 250 MB unzipped including layers; anything larger uses a container image (up to 10 GB). Layers are for shared libraries, not data.</Takeaway>

<Scene id="en-s3" label="Part 4/4" title="Amazon API Gateway for applications and partners" questions={["exam1_q49", "exam3_q52", "exam3_q53", "exam2_q58", "exam4_q44", "exam5_q32", "exam1_q57", "exam1_q11"]}>

<p class="scene-intro">Mobile apps and partners need one endpoint to call the system; that endpoint is also where requests are authenticated, authorized and throttled before they reach the backend integration.</p>

The mobile app, sales partners and the admin site all call `api.mftech.vn`. **API Gateway** runs a series of checks before a request reaches the application code. Pick a scenario and send a request:

<ApiGatewaySim client:visible />

Some other requirements:

- Chat between buyers and sellers needs a two-way connection where the backend pushes messages to clients: **WebSocket API**. With a REST API, each request is independent and no connection is kept open.
- Couriers send their location continuously for order tracking (the "Couriers stream their locations" scenario in the simulation): a REST API uses an **AWS service integration** to call Kinesis Data Streams `PutRecord` directly, with no Lambda in between, for **Amazon Managed Service for Apache Flink** (formerly Amazon Kinesis Data Analytics) to analyze the stream. Lambda only handles individual requests; it is not where data is stored or analyzed.
- Receive transactions from the app, run simple data validation, then process them, with the lowest operational cost: **REST API + Lambda** for validation, with a serverless backend behind it. There are no servers or containers to patch.

API Gateway offers several ways to authorize users. MFTech's new mobile app signs users in through an external OIDC-compliant identity provider; the backend must validate JWTs and scopes with low latency and cost, without writing authentication code. An **HTTP API with a JWT authorizer** meets this: API Gateway checks the token signature with the public key from the issuer's `jwks_uri`, validates the `iss`, `aud` and `exp` claims, and requires the token to include at least one of the route's scopes; valid claims are passed to the backend. <Takeaway>Restrict access to internal IP ranges: resource policy (API Gateway does not sit in a subnet, so there is no security group). Token validation without writing code: a REST API with a Cognito user pool authorizer, or an HTTP API with a JWT authorizer for any OIDC identity provider; a Lambda authorizer when custom logic is needed (WebSocket APIs: only on `$connect`) (HTTP APIs do not support resource policies, API keys or caching). Limits per client: usage plan + API key. Reduce backend load for repeated requests: caching. Long-running tasks: API Gateway pushes into SQS. Stream data: an AWS service integration puts it straight into Kinesis Data Streams. Two-way communication: WebSocket API.</Takeaway>
