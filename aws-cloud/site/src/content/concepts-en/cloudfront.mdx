<p class="scene-intro">An edge location does not only serve cached content; it is also the first place a request is checked, before it reaches ShopViet's system.</p>

Before forwarding a request to the origin, CloudFront can apply the following mechanisms at the edge location: TLS termination with an ACM certificate, evaluation by AWS WAF, geo restriction, signed URL/cookie validation, field-level encryption and origin selection by cache behavior. <Takeaway>Filtering application-layer attacks: AWS WAF. Restricting by country: geo restriction. Private content: signed URL (one object) or signed cookie (many objects). Sensitive data: field-level encryption. Path-based routing: cache behavior. Origin redundancy: origin group. Custom domain name: ACM certificate in us-east-1.</Takeaway>

<Scene id="en-s5" label="Part 5/6" title="Regional edge caches, uploads through CloudFront and dynamic content" questions={["exam3_q8", "exam5_q15", "exam5_q21", "exam5_q30", "exam4_q53"]}>

<p class="scene-intro">Not all content is popular and not every request only reads; CloudFront still helps with less popular content, dynamic content and even uploads.</p>

CloudFront caches at two tiers. **POPs** (edge locations) serve users directly and keep popular content. **Regional edge caches** sit between the POPs and the origin and have a larger cache than an individual POP, so objects that become less popular (older product photos, user-generated content, news that suddenly regains interest) stay close to users after a POP has removed them. When neither tier has the object, the origin response is cached at both the regional edge cache and the POP; the POPs of an area share the regional edge cache, which removes repeated requests to the origin. Both tiers belong to CloudFront and serve HTTP/HTTPS only; an application that uses UDP uses AWS Global Accelerator (part 4).

Not every request goes through a regional edge cache: requests that use PUT, POST, PATCH, OPTIONS or DELETE, and dynamic requests (as determined at request time), go from the POP directly to the origin; when the origin is S3 and the optimal regional edge cache is in the same Region as the bucket, the POP also goes to the bucket directly. Besides product images, two more ShopViet flows use the same distribution: customers upload review photos to an S3 bucket, and shipping partners look up order status through an API. Choose a scenario and a configuration to watch the request path:

<TieredPathSim client:visible />

**Uploads through CloudFront.** When the cache behavior allows PUT and POST, data enters the edge location near the user and is forwarded to the origin over the persistent connections that CloudFront keeps with the origin; CloudFront does not cache responses to these methods. For remote offices that upload and download large video files to and from one central bucket, both CloudFront (origin is the bucket's REST endpoint, OAC granted `s3:PutObject`) and S3 Transfer Acceleration improve transfer speed without splitting the data across buckets. An S3 website endpoint origin cannot serve this flow, because a website endpoint accepts only GET and HEAD and does not support OAC.

**Dynamic content.** CloudFront accelerates both cacheable and dynamic content, but when responses cannot be cached, every request reaches the origin. During a flash sale with an expected 10x traffic increase and constantly changing content, capacity must come from an **Auto Scaling group** behind the ALB; CloudFront adds no capacity to the origin. For an API used by partners worldwide, applying a managed cache policy built for static content (CachingOptimized) returns wrong data, as the simulation shows; when static IPs, TCP/UDP or fast failover between Regions are needed without changing the application, AWS Global Accelerator is the right fit.

<Takeaway>POPs keep popular content; regional edge caches keep less popular content longer. PUT, POST, PATCH, OPTIONS, DELETE and dynamic requests go from the POP directly to the origin. Uploading to S3 through CloudFront needs a cache behavior that allows PUT/POST and an OAC granted `s3:PutObject` in the bucket policy; an origin request policy only decides what information is forwarded and grants no permission. An API whose data depends on each request uses CachingDisabled (or a cache policy with a complete cache key), and the origin still scales on its own with an Auto Scaling group.</Takeaway>

</Scene>
