<Scene id="en-s1" label="Part 1/5" title="The detection delay of an alarm" questions={["exam5_q20", "exam4_q25", "exam3_q15"]}>

Each AWS service sends **metrics** to CloudWatch: EC2 CPU, Lambda invocations, the CPU of an ECS service. An **alarm** watches one metric, compares it with a threshold, and when the metric breaches the threshold for long enough it performs an **action**: sending a notification through SNS, scaling a group of resources, or acting on EC2.

A point that is often overlooked: by default, EC2 sends metrics only **every 5 minutes** (basic monitoring, free of charge); detailed monitoring sends metrics every 1 minute and is charged. Run the livestream scenario twice, once with detailed monitoring off and once with it on:

<MetricAlarmSim client:visible />

Choosing the right metric matters as much as choosing the threshold. An ECS service scales on the CPU of the service itself (namespace `AWS/ECS`, dimensions `ClusterName`, `ServiceName`). With Lambda, an unintended invocation loop can use up the account's concurrency; the Lambda documentation recommends an alarm that fires when concurrency or invocations spike (`ConcurrentExecutions`, `Invocations`), because recursive loop detection only detects loops through SQS, S3, SNS, EventBridge custom event buses or between Lambda functions.

<Takeaway>Metric data at a 1-minute period on EC2: enable detailed monitoring (charged), with no extra components to deploy. Alarm = metric + threshold + number of datapoints + action. ECS scales on the service's CPU; Lambda should have an alarm on ConcurrentExecutions.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/5" title="Recovering instances automatically with alarm actions" questions={["exam3_q38", "exam3_q57", "exam5_q19", "exam4_q16"]}>

ShopViet's warehouse management page runs on **one** EC2 instance; its scale does not yet need an Auto Scaling group. The instance occasionally fails, and restarting it manually outside working hours (for example at 3:00 a.m.) is undesirable. A CloudWatch alarm can call four EC2 actions directly: **stop**, **terminate**, **reboot**, **recover**, with no Lambda or script. In addition, for supported instance types, **simplified automatic recovery** is enabled by default at launch; CloudWatch action based recovery is an additional mechanism you configure, and it does not apply to instances in an Auto Scaling group.

EC2 has two kinds of status checks. An **instance status check** fails when the problem is inside the instance (the operating system hangs, memory is exhausted). A **system status check** fails when the AWS infrastructure the instance runs on has a problem (loss of network connectivity, loss of power, hardware or software failure on the physical host). Each kind needs a different action:

<AlarmActionSim client:visible />

<Takeaway>Problem inside the instance (instance status check): reboot action. Host problem (system status check): recover action, used only with `StatusCheckFailed_System`; instances with instance store are supported only on some instance types (M3, C3, R3, X1, X1e, X2idn, X2iedn), and the data on the instance store is lost. Recover keeps the instance ID, public IPv4, private IP, Elastic IP, instance metadata, placement group, AZ and EBS volumes; data in RAM is lost. Scale-in alarm with the default termination policy: the ASG picks the AZ with the most instances, then prefers instances using an older configuration (launch configuration, a different launch template, the oldest version of the current launch template), then the instance closest to the next billing hour; a mixed instances group also considers purchase option and allocation strategy first.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/5" title="Preserving logs when instances are replaced" questions={["exam5_q33", "exam1_q61", "exam1_q27"]}>

ShopViet's Auto Scaling group scales very frequently, with new instances replacing old ones almost every day. A user reports a payment error that happened two days ago, but the instance involved has already been terminated. In another incident, a leaked access key was used to call APIs continuously at night. Both incidents share a solution: move logs off the instance and let CloudWatch process them.

<LogPipelineSim client:visible />

Another requirement concerns the deployment location: ShopViet is expanding into e-wallets, and regulations require the data and workloads to stay in the company's data center. The engineering team still needs AWS-managed Kubernetes, along with IAM and CloudWatch as in the cloud. The solution is **AWS Outposts**: AWS installs an Outpost at the customer's site, extending AWS infrastructure, services, APIs and tools there; EC2, EBS, ECS, RDS and Amazon EKS run on premises, while AWS operates and monitors this capacity as part of the Region. Direct Connect and Local Zones still place workloads on AWS infrastructure; Snowball Edge is a device for data transfer and edge processing, and it is no longer available to new customers.

<Takeaway>Logs must be moved off an instance before it is terminated: install the CloudWatch agent to send logs to CloudWatch Logs. Near-real-time alerts on unusual API calls: CloudTrail sends to CloudWatch Logs, a metric filter counts the errors, an alarm notifies through SNS. Data that must stay on premises but still needs AWS services: Outposts.</Takeaway>

</Scene>

**CloudTrail** is the activity log: each API call is recorded as an event; by default, a trail records management events, while data events (for example operations on S3 objects) must be enabled additionally. **AWS Config** keeps the configuration history: each time a resource changes, Config records a **configuration item**, and a **Config rule** evaluates whether that configuration is compliant or noncompliant. <Takeaway>Who called which API, and when: CloudTrail (IAM operations are management events, recorded by a trail by default). Resource configuration over time and compliance: AWS Config. Make sure a trail always keeps running even when developers have root access: SCP. Certificates imported into ACM are not renewed automatically: the acm-certificate-expiration-check managed rule warns in advance. Config rules combined with remediation fix violations automatically.</Takeaway>

<Takeaway>Manage every EC2 instance with Systems Manager without creating instance profiles: Default Host Management Configuration (requires IMDSv2, SSM Agent 3.2.582.0 or later).
