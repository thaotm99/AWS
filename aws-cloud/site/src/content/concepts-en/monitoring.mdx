<Scene id="en-s1" label="Part 1/6" title="Basic monitoring and detailed monitoring for EC2 instances" questions={["exam5_q20", "exam4_q25", "exam3_q15"]}>

<p class="scene-intro">A system should detect incidents itself instead of waiting for customers to report them; this relies on continuously collected CloudWatch metrics and CloudWatch alarms with defined thresholds.</p>

Each AWS service sends **metrics** to CloudWatch: EC2 CPU, Lambda invocations, the CPU of an ECS service. An **alarm** watches one metric, compares it with a threshold, and when the metric breaches the threshold for the configured number of evaluation periods it performs an **action**: sending a notification to an SNS topic, running a scaling policy of an Auto Scaling group, or performing an EC2 action.

A point that is often overlooked: by default, EC2 sends metrics only **every 5 minutes** (basic monitoring, free of charge); detailed monitoring sends metrics every 1 minute and is charged. Run the livestream scenario twice, once with detailed monitoring off and once with it on:

<MetricAlarmSim client:visible />

Choosing the right metric matters as much as choosing the threshold. An ECS service scales on the CPU of the service itself (namespace `AWS/ECS`, dimensions `ClusterName`, `ServiceName`). With Lambda, an unintended invocation loop can use up the account's concurrency; the Lambda documentation recommends an alarm that fires when concurrency or invocations spike (`ConcurrentExecutions`, `Invocations`), because recursive loop detection only detects loops through SQS, S3, SNS, EventBridge custom event buses or between Lambda functions.

<Takeaway>Metric data at a 1-minute period on EC2: enable detailed monitoring (charged), with no extra components to deploy. Alarm = metric + threshold + number of datapoints + action. ECS scales on the service's CPU; Lambda should have an alarm on ConcurrentExecutions.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/6" title="Status checks and CloudWatch alarm actions: reboot, recover" questions={["exam3_q38", "exam3_q57", "exam5_q19", "exam4_q16"]}>

<p class="scene-intro">When an EC2 instance fails a status check, a CloudWatch alarm can reboot or recover the instance automatically, with no manual intervention.</p>

MFTECH's warehouse management page runs on **one** EC2 instance; its scale does not yet need an Auto Scaling group. The instance occasionally fails, and restarting it manually outside working hours (for example at 3:00 a.m.) is undesirable. A CloudWatch alarm can call four EC2 actions directly: **stop**, **terminate**, **reboot**, **recover**, with no Lambda or script. In addition, for supported instance types, **simplified automatic recovery** is enabled by default at launch; CloudWatch action based recovery is an additional mechanism you configure, and it does not apply to instances in an Auto Scaling group.

EC2 has two kinds of status checks. An **instance status check** fails when the problem is inside the instance (the operating system hangs, memory is exhausted). A **system status check** fails when the AWS infrastructure the instance runs on has a problem (loss of network connectivity, loss of power, hardware or software failure on the physical host). Each kind needs a different action:

<AlarmActionSim client:visible />

<Takeaway>Problem inside the instance (instance status check): reboot action. Host problem (system status check): recover action, used only with `StatusCheckFailed_System`; instances with instance store are supported only on some instance types (M3, C3, R3, X1, X1e, X2idn, X2iedn), and the data on the instance store is lost. Recover keeps the instance ID, public IPv4, private IP, Elastic IP, instance metadata, placement group, AZ and EBS volumes; data in RAM is lost. Scale-in alarm with the default termination policy: the ASG picks the AZ with the most instances, then prefers instances using an older configuration (launch configuration, a different launch template, the oldest version of the current launch template), then the instance closest to the next billing hour; a mixed instances group also considers purchase option and allocation strategy first.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/6" title="Centralizing logs with CloudWatch Logs and metric filters" questions={["exam5_q33", "exam1_q61", "exam1_q27"]}>

<p class="scene-intro">EC2 instances in an Auto Scaling group can be terminated at any time, and logs stored on an instance are lost with it; logs must be sent to CloudWatch Logs for central storage.</p>

MFTECH's Auto Scaling group scales very frequently, with new instances replacing old ones almost every day. A user reports a payment error that happened two days ago, but the instance involved has already been terminated. In another incident, a leaked access key was used to call APIs continuously at night. Both incidents share a solution: move logs off the instance and let CloudWatch process them.

<LogPipelineSim client:visible />

A trail delivers events to an S3 bucket, and can also deliver them to **CloudWatch Logs** and **EventBridge**; Kinesis is not one of these destinations. CloudTrail delivers logs within an average of about 5 minutes of an API call (this time is not guaranteed). The alarm threshold in the scenario above is known in advance (the number of calls denied with `AccessDenied`), so a metric filter and an alarm are the most direct mechanism.

**CloudTrail Insights** solves a different problem, for when the threshold is not known in advance: Insights analyzes past management and data events to establish a **baseline** of API call rates and API error rates, then generates **Insights events** when current activity deviates from the baseline. Insights is charged separately; after Insights is enabled on a trail for the first time, CloudTrail may take up to 36 hours to begin delivering Insights events. Insights events can also be sent to CloudWatch Logs together with the trail's other events.

Another requirement concerns the deployment location: MFTECH is expanding into e-wallets, and regulations require the data and workloads to stay in the company's on-premises data center. The engineering team still needs AWS-managed Kubernetes, along with IAM and CloudWatch as in the cloud. The solution is **AWS Outposts**: AWS installs an Outpost at the customer's on-premises site, extending AWS infrastructure, services, APIs and tools there; EC2, EBS, ECS, RDS and Amazon EKS run on premises, while AWS operates and monitors this capacity as part of the Region. Direct Connect and Local Zones still place workloads on AWS infrastructure; Snowball Edge is a device for data transfer and edge processing, and it is no longer available to new customers.

<Takeaway>Logs must be moved off an instance before it is terminated: install the CloudWatch agent to send logs to CloudWatch Logs. Near-real-time alerts on unusual API calls: CloudTrail sends to CloudWatch Logs, a metric filter counts the errors, an alarm notifies through SNS. Trail destinations: S3, CloudWatch Logs, EventBridge (not Kinesis). Detect API call rates or error rates that deviate from a baseline without setting a threshold: CloudTrail Insights (charged separately). Data that must stay on premises but still needs AWS services: Outposts.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/6" title="Recording API activity with CloudTrail, evaluating compliance with AWS Config" questions={["exam1_q16", "exam3_q29", "exam2_q43", "exam2_q9"]}>

<p class="scene-intro">After an incident, you need to know who did what and when, and whether the current configuration complies with policy; each question has a service that provides the data.</p>

After an incident, the MFTECH operations team needs to answer many questions; each question can be answered by only one service. Choose each question and send the query:

**CloudTrail** records the activity of users, roles and AWS services in an account: each API call is recorded as an event; by default, a trail records management events, while data events (for example operations on S3 objects) must be enabled additionally. **AWS Config** keeps the configuration history: each time a resource changes, Config records a **configuration item**, and a **Config rule** evaluates whether that configuration is compliant or noncompliant. The two services complement each other. Choose each point in time during the week of security group `sg-web`:

<ConfigTimelineSim client:visible />

Detecting a violation is different from preventing it or remediating it automatically. Three layers of guardrails that MFTECH applies to its accounts:

<GuardrailSim client:visible />

The `org-audit-trail` trail in the scenario above can be created as an **organization trail**. An organization trail can only be created from the **management account** or a CloudTrail **delegated administrator** account; it is applied automatically to every member account, including accounts that join the organization later. Users in member accounts can see the organization trail, but cannot delete it, turn logging on or off, or change it in any way. By contrast, a trail that a developer creates inside their own account is an ordinary trail of that account, and the root user can delete it; for trails in member accounts, an SCP remains the necessary layer of protection.

For certificates, ACM offers two more signal sources besides the Config rule. The **`DaysToExpiry`** metric (namespace `AWS/CertificateManager`, dimension `CertificateArn`) is published by ACM to CloudWatch twice per day for every certificate until it expires; because the metric is tied to a single ARN, each certificate needs its own alarm, and every certificate imported later needs one more alarm. EventBridge receives a daily **ACM Certificate Approaching Expiration** event, starting 45 days before expiration for private or imported certificates and 30 days for public certificates. The `acm-certificate-expiration-check` managed rule evaluates every certificate in the account against the same threshold and keeps a compliance history, with no alarm to create per certificate.

To apply the same set of Config rules to many accounts, MFTECH uses a **conformance pack**: a collection of Config rules and remediation actions, written in a YAML template and deployed as a single entity in an account and Region or across the whole organization. When it is deployed from the management account, member accounts cannot modify those rules and remediation actions. A conformance pack only evaluates and remediates configuration; it does not create accounts and does not build shared network infrastructure.

<Takeaway>Who called which API, and when: CloudTrail (IAM operations are management events, recorded by a trail by default). Resource configuration over time and compliance: AWS Config. Make sure a trail always keeps running even when developers have root access: SCP. An organization trail can only be created from the management account or a delegated administrator; member accounts cannot change it. Certificates imported into ACM are not renewed automatically: the acm-certificate-expiration-check managed rule warns in advance (the DaysToExpiry metric needs one alarm per certificate). Config rules combined with remediation fix violations automatically; a conformance pack deploys one set of rules and remediations to the whole organization.</Takeaway>

</Scene>
