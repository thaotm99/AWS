<Takeaway>Block storage (EBS): a disk dedicated to one instance in one AZ, charged for provisioned capacity. File storage (EFS, FSx): shared by many instances; EFS scales automatically and charges for the data actually stored. Object storage (S3): accessed through an API; S3 Standard stores data across at least 3 AZs. S3 Standard and EFS Regional are both designed for 99.999999999% (11 nines) durability. At us-east-1 list prices (10/2026), per GB-month: S3 Standard $0.023, EFS Standard $0.30, EBS gp2 $0.10 and gp3 $0.08 charged on provisioned capacity. For 1 GB of data on a 100 GB volume: S3 < EFS < EBS. Prices vary by Region; always compare with current pricing.</Takeaway>

<Scene id="en-s2" label="Part 2/5" title="Choosing an EBS volume for the database" questions={["exam3_q27", "exam5_q22", "exam1_q44", "exam6_q24", "exam4_q15", "exam5_q64", "exam5_q16", "exam5_q40"]}>

<p class="scene-intro">The database's disk sets the read and write speed of the whole system; AWS offers several disk types that differ in performance and price.</p>

ShopViet's order database runs on EC2, and its IOPS needs keep growing. Adjust the IOPS slider and turn on requirements to see the suitable volume type:

<VolumeChooser client:visible />

**gp2** performance scales with size: a baseline of 3 IOPS per GiB (minimum 100, maximum 16,000 IOPS). gp2 volumes smaller than 1 TiB can burst to 3,000 IOPS using **I/O credits**: each volume starts with 5.4 million credits (also the cap), spends credits while the load is above the baseline, and earns them back when the load drops below it. **gp3** volumes do not burst: 3,000 IOPS and 125 MiB/s are an included baseline sustained indefinitely, and you provision extra IOPS and throughput independently of size. <Takeaway>Default choice: gp3 (3,000 IOPS baseline without credits, up to 80,000 IOPS; gp2 up to 16,000 IOPS, a 3 IOPS/GiB baseline, and volumes under 1 TiB burst to 3,000 IOPS with I/O credits, tracked by the BurstBalance metric). Consistent IOPS for I/O-intensive databases, more than 80,000 IOPS, or Multi-Attach: io1/io2 (io2 Block Express up to 256,000 IOPS). Large sequential reads: st1; infrequently accessed data: sc1; the two HDD types cannot be used as boot volumes. Quickly creating a test environment from a snapshot: fast snapshot restore.</Takeaway>

Credits accrue while the load is below the baseline, up to 2.1 TiB (file systems under 1 TiB) or 2.1 TiB per TiB stored. Data moved to IA does not count toward the baseline. <Scene id="en-s5" label="Part 5/5" title="Accessing S3 data through a file interface" questions={["exam3_q5", "exam4_q24", "exam5_q28", "exam5_q47", "exam3_q32"]}>

<p class="scene-intro">Some older applications can only read and write files in folders while the data lives in S3; they need a translation layer to use it without being rewritten.</p>

The ShopViet data team keeps all product images and the recommendation model's training data in S3. Some older applications only read and write files and cannot call the S3 API. **Mountpoint for Amazon S3** is an open source file client that mounts a bucket as a local directory on Linux and translates file operations (`open`, `read`) into S3 API calls. Mountpoint is not a fully POSIX file system: try common operations on Mountpoint and on EFS:

<MountpointSim client:visible />

Mountpoint suits large-scale, read-heavy applications: data lakes, machine learning training, image rendering, ETL. It can read objects in every storage class except S3 Glacier Flexible Retrieval, S3 Glacier Deep Archive and the two Archive tiers of S3 Intelligent-Tiering. For repeated reads of the same data you can opt in to a local cache (instance storage or EBS) or a shared cache in S3 Express One Zone. For workloads that need full POSIX support on S3 data, AWS recommends **FSx for Lustre** linked to the bucket. Choose a file interface for each situation:

**Amazon S3 Files** is a shared file system, built using Amazon EFS, linked to a bucket or a prefix: applications read and write files with full file system semantics, and S3 Files synchronizes changes between the file system and the bucket. An S3 file system can be mounted on EC2 and Lambda, and declared as a volume (`s3filesVolumeConfiguration`) for ECS tasks on Fargate, ECS Managed Instances and EC2; a task IAM role and encryption in transit are mandatory. Older study material states that "S3 cannot be mounted as a file system"; with S3 Files, S3 data can be mounted through a separate file system resource, but the bucket itself is still not a volume type you attach to a task. For microservices that need a shared POSIX directory across AZs and whose data does not need to live in S3, EFS remains the most direct option.

<Takeaway>Fargate tasks: EFS, EBS, bind mount (ephemeral storage) or S3 Files volumes; no script that mounts a bucket. Mountpoint for Amazon S3: a Linux file client that reads large files and creates new files at S3 throughput; it cannot modify existing files or delete directories, and does not support symbolic links or file locking.
