ShopViet runs three web servers in two AZs behind a load balancer. A user uploads a product video to any one server, and other users must be able to watch that video whichever server they are routed to. Try storing the video in three places:

<SharedStorageSim client:visible />

When several AWS accounts (for example, the account of each sub-shop) need to mount the same folder, EFS still works: add a file system policy that grants access to the other account, and connect the two VPCs with VPC peering or a transit gateway.

<Takeaway>Block storage (EBS): a disk dedicated to one instance in one AZ, charged for provisioned capacity. File storage (EFS, FSx): shared by many instances; EFS scales automatically and charges for the data actually stored. Object storage (S3): accessed through an API; S3 Standard stores data across at least 3 AZs. S3 Standard and EFS Regional are both designed for 99.999999999% (11 nines) durability. Cost comparisons must use the current pricing of each Region, and keep in mind that EBS charges for provisioned capacity, including the unused part.</Takeaway>

</Scene>

<Takeaway>Default choice: gp3 (up to 80,000 IOPS; gp2 up to 16,000 IOPS). Consistent IOPS for I/O-intensive databases, more than 80,000 IOPS, or Multi-Attach: io1/io2 (io2 Block Express up to 256,000 IOPS). Large sequential reads: st1; infrequently accessed data: sc1; the two HDD types cannot be used as boot volumes. Quickly creating a test environment from a snapshot: fast snapshot restore.</Takeaway>

<Scene id="en-s3" label="Part 3/4" title="Configuring EFS for the workload" questions={["exam2_q64", "exam4_q55", "exam3_q11", "exam2_q60", "exam6_q39", "exam4_q24", "exam1_q12", "exam5_q47"]}>

After deploying EFS, ShopViet has operational issues to solve: adjusting the configuration under heavy load, optimizing the cost of storing old files, and controlling who can mount. Choose each scenario:

<RequirementPicker client:visible items={[
  { need: "A big data job runs in parallel on a very large number of instances, all reading and writing EFS", answer: "Performance mode: General Purpose", why: "AWS recommends General Purpose for all file systems. Max I/O is a previous-generation performance mode for highly parallel workloads that can tolerate higher latency; Max I/O does not support Elastic throughput or One Zone file systems." },
  { need: "Spiky, unpredictable load, and you do not want to provision throughput yourself", answer: "Elastic throughput (default)", why: "Throughput scales up and down automatically with the load; you pay only for the data and metadata read and written, with no burst credits. Bursting throughput instead scales with the amount of storage in the Standard class (50 KiBps per GiB)." },
  { need: "A small configuration folder (under 1 TB) that is read and written constantly", answer: "Provisioned throughput", why: "Provisions a fixed level of throughput, independent of file system size or burst credit balance. Suits cases where the performance requirement is known in advance." },
  { need: "Old order images are rarely accessed but sometimes must be retrieved immediately; cost must be optimized", answer: "EFS Infrequent Access (lifecycle to IA)", why: "A lower-cost storage class for rarely accessed files that can still be read immediately." },
  { need: "Each web server accesses EFS with the lowest latency", answer: "A mount target in each AZ; EC2 uses the mount target in its own AZ", why: "Traffic does not have to cross to another AZ." },
  { need: "Only the web servers may mount; other servers are denied", answer: "Security group + IAM policy", why: "The mount target's security group controls network access; IAM controls mount permissions." },
  { need: "The risk that a Region-level outage causes data loss on EFS", answer: "AWS Backup copies to another Region", why: "Scheduled backups copied to another Region." },
]} />

<Takeaway>EFS: an NFS file system shared across multiple AZs. Recommended configuration: General Purpose performance mode + Elastic throughput; Max I/O is previous generation. Throughput needs known in advance, independent of storage size: Provisioned throughput. Rarely accessed files: the IA class. Mount targets in the same AZ to reduce latency.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/4" title="Choosing a file system for four groups of users" questions={["exam2_q12", "exam2_q56", "exam1_q65", "exam3_q5", "exam3_q43", "exam3_q56", "exam1_q24", "exam3_q61", "exam3_q26"]}>

Besides EFS, AWS offers three **FSx** types for specialized needs. Each of ShopViet's four user groups has three must-have requirements. Try mounting each file system for each group to find the file system that meets all the requirements:

<FsxSim client:visible />

When the office needs to keep an on-premises SMB file share but store the data on S3, use **S3 File Gateway** (see the Storage Gateway lesson).

<Takeaway>Windows, SMB, NTFS, Active Directory, DFS: FSx for Windows File Server. HPC, parallel reads, loading data from S3: FSx for Lustre. Already on NetApp, needs NFS + SMB + iSCSI: FSx for NetApp ONTAP. A simple shared folder for Linux: EFS.</Takeaway>
