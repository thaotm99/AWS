<Scene id="en-s1" label="Part 1/6" title="Working out the permissions a policy grants" questions={["exam2_q37", "exam2_q38", "exam2_q48", "exam2_q54", "exam1_q58"]}>

<p class="scene-intro">Every permission on AWS is described by a policy, a JSON document that lists which actions are allowed or denied on which resources; reading policies is a skill you need before granting access.</p>

Before attaching a policy written by someone else to a MFTech user or role, you must determine exactly what permissions it grants. Choose a policy, predict the result, then send each request to check.

<PolicyReader client:visible />

Reading a policy correctly is half the job; the other half is granting **exactly** the permissions needed (least privilege). MFTech's finance team must list the mftech-reports bucket and delete old reports, nothing more. The current policy cannot delete objects yet. Choose the statement to add and watch which requests are allowed.

<LeastPrivilegeSim client:visible />

<Takeaway>When no Allow statement matches, the request is implicitly denied (implicit deny). aws:SourceIp is the requester's IP address; aws:RequestedRegion is the Region that receives the API call. ListBucket applies to the bucket ARN; GetObject/DeleteObject apply to bucket/*. A wildcard inside an action name (`s3:*Object`), `s3:*`, and a trailing `*` in an ARN (`bucket*`, which also matches `/` and other buckets with the same prefix) all easily grant excess permissions.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/6" title="Policy evaluation logic: the policy types that evaluate a request" questions={["exam3_q59", "exam1_q25", "exam2_q39", "exam2_q16"]}>

<p class="scene-intro">A request to AWS succeeds only when every relevant permission layer allows it; a single layer that denies it blocks the request.</p>

A request can be stopped at several layers: an Organizations **SCP** limits the whole account, a **permissions boundary** limits the maximum permissions of a user/role, an **identity policy** grants permissions, and for cross-account access, a **resource policy** (for example a bucket policy) must also allow it. Change each layer and watch the result.

<PolicyEvaluator client:visible />

<Takeaway>An explicit deny always takes precedence. SCPs restrict even the root user of a member account but do not affect service-linked roles. A permissions boundary prevents privilege escalation (a developer attaching AdministratorAccess to themselves). Cross-account access: needs both an identity policy on the caller's side and a resource policy on the resource's side.</Takeaway>

</Scene>

<Scene id="en-s5" label="Part 5/6" title="Centralized workforce access with IAM Identity Center" questions={["exam1_q10", "exam4_q4", "exam6_q10"]}>

<p class="scene-intro">Employees already have identities in the company's identity provider (IdP); instead of creating separate AWS sign-in credentials for each person, federation lets them sign in to AWS with those same identities.</p>

MFTech has 6 accounts in Organizations and manages its staff in on-premises Active Directory; a subsidiary uses Microsoft Entra ID. Staff need access to the right accounts for their job, with their own corporate identity. AWS recommends that human users access AWS through **federation** with an identity provider and use temporary credentials; for centralized access management across many accounts, AWS recommends **IAM Identity Center**.

Identity Center has exactly one identity source per organization: the Identity Center directory, Active Directory (through **AD Connector** or **AWS Managed Microsoft AD**), or an external IdP through **SAML 2.0**. Permissions are defined as **permission sets** (collections of IAM policies) and assigned to users or groups for each account. Choose a scenario and compare the options.

<FederationSim client:visible />

The directory used by Identity Center must be in the Organizations management account (or the Identity Center delegated administrator account). With AWS Managed Microsoft AD, Identity Center must be enabled in the same Region as the directory.

<Takeaway>Many accounts, existing identities: IAM Identity Center, with permission sets assigned to groups. On-premises AD with one domain: AD Connector; several domains or forests: AWS Managed Microsoft AD with a two-way trust. External IdP (Okta, Entra ID): SAML 2.0 for authentication, SCIM to provision users and groups. An IAM SAML identity provider must be in the same account as the role, so it must be configured again in every account.</Takeaway>

</Scene>
