<Scene id="en-s2" label="Part 2/4" title="The permission layers that evaluate a request" questions={["exam3_q59", "exam1_q25", "exam2_q39", "exam2_q16"]}>

A request can be stopped at several layers: an Organizations **SCP** limits the whole account, a **permissions boundary** limits the maximum permissions of a user/role, an **identity policy** grants permissions, and for cross-account access, a **resource policy** (for example a bucket policy) must also allow it. Change each layer and watch the result.

<PolicyEvaluator client:visible />

<Takeaway>An explicit deny always takes precedence. SCPs restrict even the root user of a member account but do not affect service-linked roles. A permissions boundary prevents privilege escalation (a developer attaching AdministratorAccess to themselves). Cross-account access: needs both an identity policy on the caller's side and a resource policy on the resource's side.</Takeaway>

</Scene>

The same principle applies to other cases:

  { need: "A Lambda function that processes orders in account A reads images in S3 in account B", answer: "Lambda execution role + bucket policy in account B",

    why: "Each Kubernetes service account is mapped to its own IAM role, ensuring least privilege for each Pod." },
  { need: "A Lambda function connects to RDS PostgreSQL without storing a password in the source code", answer: "IAM database authentication + an IAM role for Lambda",
    why: "Lambda uses the role to get a short-lived authentication token when connecting to RDS." },
  { need: "Define which principals can assume a role", answer: "The role's trust policy",

<Takeaway>Applications on AWS use IAM roles, not access keys. Cross-account access: create a role in the target account and assume it.</Takeaway>
