<p class="scene-intro">Data is accessed at very different rates: product images are viewed constantly, old invoices almost never; S3 lets each kind sit at a price that fits how often it is read.</p>

S3 cost has two main components: a storage charge per GB and a data retrieval charge. The lower a storage class's storage charge, the higher its retrieval charge or the longer its retrieval time. Choose each type of ShopViet data to see the right storage class:

Lifecycle transitions objects in a waterfall model: one way only, down to lower-cost storage classes. Try a few pairs, for example Intelligent-Tiering → Standard or One Zone-IA → Standard-IA:

<LifecycleValidator client:visible />

**When objects can move to an IA class.** Since July 16, 2026, a lifecycle rule can transition objects to Standard-IA or One Zone-IA as soon as 0 days after creation. Before that date, S3 required objects to stay at least 30 days in Standard before a transition to these two classes; study material written before July 2026 relies on the old rule and therefore rules out "transition after 7 days" options. The 30-day minimum storage duration of Standard-IA and One Zone-IA is unchanged: it is a billing rule for objects that leave the IA class early, not a condition for the transition. In addition, by default lifecycle does not transition objects smaller than 128 KB to any storage class.

A lifecycle rule does not have to apply to the whole bucket. The rule's **filter** element selects the objects it acts on: by key **prefix**, by one or more **object tags** (each matching both key and value exactly), or by object size; when several conditions are combined, S3 applies a logical AND. A filter has only one prefix, so to apply an action to several different prefixes you create several rules. An empty filter applies to every object in the bucket. ShopViet's product image bucket keeps originals under `images/` and thumbnails under `thumbnails/`; the two groups have different access patterns:

<LifecycleFilterSim client:visible />

<Takeaway>Frequent access: Standard. Unpredictable access patterns: Intelligent-Tiering. Infrequent access that needs immediate retrieval: Standard-IA (One Zone-IA if the data can be regenerated and losing it with an AZ is acceptable). Long-term archive: the Glacier classes. Lifecycle does not transition objects back up. Only part of the data changes its access pattern: a lifecycle rule with a prefix or tag filter. Standard-IA and One Zone-IA have a 30-day minimum storage duration: an object deleted, overwritten or transitioned earlier is still charged for the full 30 days. Since July 16, 2026, a rule can transition to Standard-IA or One Zone-IA from day 0 (before that, objects had to stay in Standard for at least 30 days).</Takeaway>

<Scene id="en-s2" label="Part 2/7" title="Protecting invoices from deletion: versioning and Object Lock" questions={["exam1_q20", "exam5_q50", "exam1_q56", "exam4_q64", "exam5_q39"]}>

<p class="scene-intro">Some data must stay untouched for years by regulation; it needs a mechanism that prevents deletion or overwriting, whether by mistake or by an administrator.</p>

Regulations require ShopViet to keep invoices for many years. The risk of data loss comes from an employee deleting by mistake, a faulty cleanup script, or an administrator deleting on purpose. Choose how the bucket is protected and who deletes, then see which layer of protection keeps the invoice:

<DeleteGuardSim client:visible />

A retention period is set in one of two ways. When you apply it **explicitly** to an object version, the request carries a **Retain Until Date**, and S3 stores that date in the version's metadata. With a **bucket default retention**, you specify only a **duration** (days or years); S3 computes the Retain Until Date by adding that duration to the version's creation time. If a PUT request carries its own retention mode and period, those explicit settings **override** the bucket default. A retention period can be extended with a later Retain Until Date; in Compliance mode it cannot be shortened.

<RetentionSim client:visible />

Retention periods apply to individual object versions, so versions of the same key can have different retention modes and periods. **ACLs** cannot replace this mechanism: an ACL only defines which accounts or groups are granted access and the type of access; it has no notion of a retention period, so it cannot enforce WORM compliance controls. For data stored in an **Amazon Glacier** vault (a standalone vault service with its own API from 2012, distinct from the S3 Glacier storage classes), each vault can have one **vault access policy** and one **Vault Lock policy**, both written in the IAM policy language. The vault access policy is for ordinary access controls that are not compliance related and can be changed at any time. The Vault Lock policy is for compliance controls, for example denying `glacier:DeleteArchive` for archives younger than 365 days (condition key `ArchiveAgeInDays`). Locking a vault takes two steps: attaching the Vault Lock policy puts the lock in the **in-progress** state and returns a lock ID; within **24 hours** you validate the policy and complete the lock with that lock ID, otherwise the policy is deleted (if the policy is not right, you can stop and restart the process). Once completed, the Vault Lock policy **can no longer be changed or deleted**. Amazon Glacier is no longer open to new customers; existing data remains stored, and AWS recommends the S3 Glacier storage classes for long-term archives, where S3 Object Lock provides WORM protection.

<Takeaway>Protect against accidental deletes: versioning (a simple delete only adds a delete marker). Require extra authentication for permanent deletes: MFA Delete. No one can delete, including root: Object Lock Compliance mode. Governance mode still lets users with bypass permission delete. Retention with no end date, for example during a dispute: legal hold. A bucket default retention is a duration; an explicit retention on a version is a Retain Until Date and overrides the default. Amazon Glacier vaults: a Vault Lock policy (completed within 24 hours, immutable afterwards), unlike a vault access policy (can be changed).</Takeaway>

</Scene>

An **ACL** is S3's legacy access control mechanism: every bucket and object has an ACL attached as a subresource that defines which AWS accounts or groups are granted access and the type of access. An ACL is not a JSON policy like a bucket policy or an IAM role trust policy. With Object Ownership = bucket owner enforced (the default), all ACLs are disabled, requests to set ACLs fail with the `AccessControlListNotSupported` error code, and access is managed only with policies. AWS recommends keeping ACLs disabled except when you need to control access to each object individually.

<Takeaway>Grant permissions to another account: bucket policy (up to 20 KB). Grant extra permissions to a set of IAM users in the same account: an IAM group. Many teams, one prefix each: access points; an access point does not change the network path, so private access to S3 from a VPC needs a VPC endpoint ([VPC lesson, VPC endpoints](/concepts/vpc/#en-s4)). Organization-wide monitoring: Storage Lens. New buckets use Object Ownership = bucket owner enforced, with ACLs disabled.</Takeaway>

<Scene id="en-s4" label="Part 4/7" title="Managing encryption keys" questions={["exam2_q10", "exam6_q51", "exam3_q24", "exam1_q22", "exam5_q46"]}>

<p class="scene-intro">Data in S3 is always encrypted; what must be decided is who holds the encryption key and whether each use of it must be logged.</p>

Every encryption method makes data at rest unusable without the key. The differences lie in which component performs the encryption, where the key is stored, and whether each use of the key is logged. Choose a ShopViet requirement, upload three invoices and see where the data becomes encrypted:

<EncryptionSim client:visible />

When the invoice archive moves from the data center to S3, the security team requires every file to be encrypted with a different key. This does not require splitting the data across several buckets: with server-side encryption, S3 encrypts **each object with a unique key**, including with the default SSE-S3. **Client-side encryption** is a different approach: the application uses the **Amazon S3 Encryption Client** to encrypt data locally before sending it; S3 receives data that is already encrypted, plays no role in encrypting or decrypting it, and does not recognize the object as encrypted. The Encryption Client also encrypts every object with a unique data key, but the application must integrate the library and manage the wrapping key itself, so it fits only when data must be encrypted before it leaves the company's systems.

<Takeaway>Simplest configuration: SSE-S3 (a unique key per object). Need to audit key usage: SSE-KMS (enable S3 Bucket Key to reduce the cost of KMS calls). Keys must be kept at the company but S3 performs the encryption: SSE-C (since April 2026, SSE-C is blocked by default on new buckets; re-enable it with PutBucketEncryption). Data must be encrypted before it is sent to AWS: client-side encryption with the Amazon S3 Encryption Client.</Takeaway>

</Scene>

<Scene id="en-s5" label="Part 5/7" title="Optimizing upload speed and peak-load capacity" questions={["exam4_q14", "exam1_q64", "exam1_q18", "exam1_q40", "exam1_q51", "exam6_q20", "exam5_q21", "exam3_q37"]}>

<p class="scene-intro">As data and users grow, upload speed and peak-time load become problems; S3 has a specific feature for each situation.</p>

This part presents four problems ShopViet ran into as data volume and the number of users grew, plus the cost of one upload through Transfer Acceleration. Run each scenario, then turn on the matching S3 feature to compare the results:

<UploadSim client:visible />

**Transfer Acceleration speeds up both directions.** According to the S3 FAQs, Transfer Acceleration speeds up long-distance transfers **to and from** a single bucket (uploads and downloads both go to the `<bucket>.s3-accelerate.amazonaws.com` endpoint) and helps most with larger objects. When ShopViet opens a portal where studios on several continents both upload and download raw videos of up to 10 GB, enabling Transfer Acceleration on the bucket improves both directions; adding CloudFront is not required. AWS suggests considering CloudFront's PUT/POST when objects or the data set are smaller than 1 GB; for larger files, Transfer Acceleration gives higher throughput. CloudFront fits when the same content is viewed repeatedly by many people (images, promotional videos), because edge locations cache that content.

<Takeaway>Large files: multipart upload (required for objects over 5 GB). Large files (about 1 GB and up) moved over long distances to or from one bucket: Transfer Acceleration, which speeds up both uploads and downloads (goes through CloudFront edge locations; can incur additional data transfer charges); files under 1 GB: consider CloudFront PUT/POST. Too many requests: spread keys across many prefixes. Only part of a file is needed: byte-range fetch (a `Range` header on a GET request). Cost: data transfer in from the internet to S3 is free; the Transfer Acceleration charge is in addition to data transfer pricing and applies only to transfers that are accelerated. S3 Select (SQL queries on the content of one CSV, JSON or Parquet object) is no longer available to new customers.</Takeaway>

</Scene>

<Scene id="en-s6" label="Part 6/7" title="Static websites on S3: the website endpoint and a failover page" questions={["exam5_q15", "exam1_q62", "exam4_q53", "exam5_q56"]}>

<p class="scene-intro">A website made only of HTML, CSS and images needs no application server; the files can be served straight from S3.</p>

ShopViet's seasonal promotion site consists only of HTML, CSS, images and client-side scripts, so it can be served directly from the `shopviet-promo` bucket. When you enable **static website hosting**, the bucket gets a Region-specific **website endpoint** (`http://<bucket>.s3-website-<region>.amazonaws.com` or `…s3-website.<region>…`, depending on the Region), separate from the **REST API endpoint** that applications send API requests to. The two endpoints handle the same request very differently. Send each request through each endpoint to compare:

<WebsiteEndpointSim client:visible />

The website endpoint is optimized for browsers: it returns the index document at the root, returns an HTML document (the custom error document for 4XX errors) on errors and supports redirects, but it serves only publicly readable content, accepts only GET and HEAD, and does not support HTTPS. AWS recommends **AWS Amplify Hosting**, or putting **CloudFront** in front, when you need HTTPS. A static website does not replace an application tier either: S3 does not run server-side scripts, so pages with dynamic content that changes constantly (a cart, real-time prices) still need EC2 in an Auto Scaling group or an equivalent service to scale with traffic.

<Takeaway>Static website (HTML, CSS, images, client-side scripts): S3 static website hosting. Website endpoint: GET/HEAD only, public content only, returns the index document and HTML error pages, no HTTPS.
