S3 cost has two main components: a storage charge per GB and a data retrieval charge. The lower a storage class's storage charge, the higher its retrieval charge or the longer its retrieval time. Choose each type of ShopViet data to see the right storage class:

  { need: "Intermediate files of the order-processing pipeline, read again constantly", answer: "S3 Standard",

  { need: "Invoices: accessed frequently in the first month, then rarely but must be retrievable immediately; kept for 5 years and then deleted", answer: "Lifecycle to Standard-IA after 30 days + expiration",

  { need: "Raw logs that have already been processed, kept only as a backup, almost never read again", answer: "Lifecycle to Glacier Deep Archive",

Lifecycle transitions objects in a waterfall model: one way only, down to lower-cost storage classes. Try a few pairs, for example Intelligent-Tiering → Standard or One Zone-IA → Standard-IA:

<LifecycleValidator client:visible />

<Takeaway>Frequent access: Standard. Unpredictable access patterns: Intelligent-Tiering. Infrequent access that needs immediate retrieval: Standard-IA (One Zone-IA if the data can be regenerated). Long-term archive: the Glacier classes. Lifecycle does not transition objects back up. Standard-IA and One Zone-IA have a 30-day minimum storage duration: an object deleted, overwritten or transitioned earlier is still charged for the full 30 days.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/5" title="Protecting invoices from deletion: versioning and Object Lock" questions={["exam1_q20", "exam5_q50", "exam1_q56", "exam4_q64", "exam5_q39"]}>

Regulations require ShopViet to keep invoices for many years. The risk of data loss comes from an employee deleting by mistake, a faulty cleanup script, or an administrator deleting on purpose. Choose how the bucket is protected and who deletes, then see which layer of protection keeps the invoice:

<DeleteGuardSim client:visible />

The retention period (**Retain Until Date**) is set on each object version, so each version can have its own mode and retention period. For data stored in an **Amazon Glacier** vault (a standalone vault service, distinct from the S3 Glacier storage classes and no longer open to new customers), **Vault Lock** works in a similar way: once a Vault Lock policy is locked, it can no longer be changed or deleted.

<Takeaway>Protect against accidental deletes: versioning (a simple delete only adds a delete marker). Require extra authentication for permanent deletes: MFA Delete. No one can delete, including root: Object Lock Compliance mode. Governance mode still lets users with bypass permission delete. Retention with no end date, for example during a dispute: legal hold.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/5" title="Managing encryption keys" questions={["exam2_q10", "exam6_q51", "exam3_q24", "exam1_q22", "exam5_q46"]}>

Every encryption method makes data at rest unusable without the key. The differences lie in which component performs the encryption, where the key is stored, and whether each use of the key is logged. Choose a ShopViet requirement, upload three invoices and see where the data becomes encrypted:

<EncryptionSim client:visible />

<Takeaway>Simplest configuration: SSE-S3. Need to audit key usage: SSE-KMS (enable S3 Bucket Key to reduce the cost of KMS calls). Keys must be kept at the company but S3 performs the encryption: SSE-C (since April 2026, SSE-C is blocked by default on new buckets; re-enable it with PutBucketEncryption). Your own encryption algorithm: client-side encryption.</Takeaway>

</Scene>

For distant users who both download videos and upload files, combine both: **CloudFront** for downloads and **S3 Transfer Acceleration** for uploads.

<Takeaway>Large files: multipart upload (required for objects over 5 GB). Distant uploaders: Transfer Acceleration (goes through CloudFront edge locations; can incur additional data transfer charges). Too many requests: spread keys across many prefixes. Only part of a file is needed: byte-range fetch.</Takeaway>
