An **Application Load Balancer** (ALB) inspects the content of HTTP requests: path, domain name, headers. A **Network Load Balancer** (NLB) works at layer 4 (TCP, UDP, TLS and QUIC listeners) and does not inspect HTTP content; an NLB has one IP per AZ (which can be an Elastic IP) and can handle millions of requests per second. Try each ShopViet requirement, first with an ALB and then with an NLB:

<Takeaway>Web applications that need routing by URL or domain name: ALB. Plain TCP/UDP, a fixed IP for partners, PrivateLink: NLB. Servers sit in private subnets; only the load balancer is in public subnets. Multiple Regions: one load balancer per Region, with Route 53 or Global Accelerator in front.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/4" title="Share of traffic per target" questions={["exam3_q14", "exam4_q59"]}>

During a sale, ShopViet urgently adds servers in AZ B, while AZ A still has only 1 server. The question: is the single server in AZ A overloaded? Adjust the sliders and turn cross-zone on or off. Try 1 server in AZ A and 4 in AZ B; then 4 and 6.

<CrossZoneCalc client:visible />

<Takeaway>DNS splits traffic evenly between the load balancer nodes in each AZ. With cross-zone on: load is spread evenly across all targets. With cross-zone off: each AZ gets an equal share, which is then spread across the targets in that AZ, so an AZ with fewer servers gets overloaded. Defaults: ALB always has cross-zone on at the load balancer level (it can be turned off at the target group level); NLB and GWLB have it off.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/4" title="One ALB for many services and many domain names" questions={["exam1_q48", "exam4_q40", "exam4_q57", "exam2_q17", "exam1_q6"]}>

ShopViet splits its system into an orders service, a products service and promotional microsites, each with its own target group. They all still sit behind **one** ALB. Each request goes through the HTTPS listener: certificate selection (SNI), AWS WAF, then the listener rule whose conditions (path, host) match performs the rule's actions: authentication (if there is an authenticate action), then forward to a target group. Pick a scenario and send a request:

<AlbRuleSim client:visible />

<Takeaway>Listener rules route by path (`/orders/*`) and host (`*.shopviet.vn` matches `khuyenmai.shopviet.vn` but not the apex domain `shopviet.vn`). Multiple HTTPS domain names on one listener: add multiple certificates; the ALB selects a certificate using SNI. The ALB integrates authentication with Cognito and supports associating AWS WAF.</Takeaway>

</Scene>

<Scene id="en-s4" label="Part 4/4" title="Targets that work normally but are marked unhealthy" questions={["exam4_q26", "exam5_q1", "exam2_q18", "exam3_q13"]}>

The ALB marks i-2 as unhealthy, while an engineer who connects to the instance over SSH confirms the application still works. The load balancer relies only on **health check** results: it calls a path on each target periodically (every 30 seconds by default for the instance or ip target type). Follow the health check's path and see where it is blocked:

<HealthCheckSim client:visible />

<Takeaway>Target unhealthy while the application still works: check whether the security group allows traffic from the load balancer and whether the health check path is correct. For the ASG to replace instances the load balancer marks as failed: switch the ASG's health check to the ELB type.</Takeaway>

</Scene>
