<Scene id="en-s1" label="Part 1/7" title="Load balancer types: ALB and NLB" questions={["exam1_q2", "exam1_q48", "exam4_q9", "exam6_q43", "exam1_q39", "exam6_q56", "exam6_q7", "exam5_q4"]}>

<p class="scene-intro">A load balancer is the shared entry point: it receives requests from clients and distributes them across multiple targets, such as EC2 instances. The two main types differ in whether they inspect the request content or only forward connections.</p>

An **Application Load Balancer** (ALB) inspects the content of HTTP requests: path, domain name, headers. A **Network Load Balancer** (NLB) works at layer 4 (TCP, UDP, TLS and QUIC listeners) and does not inspect HTTP content; an NLB has one IP per AZ (which can be an Elastic IP) and can handle millions of requests per second. Besides EC2, a target group with the **ip** target type also accepts on-premises resources connected through Direct Connect or Site-to-Site VPN (private IPs only). Try each MFTECH requirement, first with an ALB and then with an NLB:

MFTECH plans to expand to a Region in the United States. The question: can one load balancer distribute load across both Regions?

<Takeaway>Web applications that need routing by URL or domain name: ALB. Plain TCP/UDP, a fixed IP for partners, PrivateLink: NLB. UDP servers in a data center: NLB with a UDP listener and the ip target type (private IPs, over Direct Connect or VPN). EC2 instances sit in private subnets; only the load balancer is in public subnets. Multiple Regions: one load balancer per Region, with Route 53 or Global Accelerator in front.</Takeaway>

<Scene id="en-s2" label="Part 2/7" title="Cross-zone load balancing" questions={["exam3_q14", "exam4_q59"]}>

<p class="scene-intro">A load balancer has nodes in several AZs; how traffic is distributed between those AZs decides whether each target receives many requests or few.</p>

During a sale, MFTECH urgently adds EC2 instances in AZ B, while AZ A still has only 1 instance. The question: is the single target in AZ A overloaded? Adjust the sliders and turn cross-zone load balancing on or off. Try 1 target in AZ A and 4 targets in AZ B; then 4 and 6.

<CrossZoneCalc client:visible />

<Takeaway>DNS splits traffic evenly between the load balancer nodes in each AZ. With cross-zone on: load is spread evenly across all targets. With cross-zone off: each AZ gets an equal share, which is then spread across the targets in that AZ, so targets in an AZ with fewer targets receive more load. Defaults: ALB always has cross-zone on at the load balancer level (it can be turned off at the target group level); NLB and GWLB have it off.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/7" title="Listener rules for your Application Load Balancer" questions={["exam1_q48", "exam4_q40", "exam4_q57", "exam2_q17", "exam1_q6", "exam3_q53", "exam6_q60"]}>

<p class="scene-intro">When a system splits into several services, one load balancer can still front them all and send each request to the right service by path or domain name.</p>

MFTECH splits its system into an orders service, a products service and promotional microsites, each with its own target group. They all still sit behind **one** ALB. Each request goes through the HTTPS listener: certificate selection (SNI), AWS WAF, then the listener rule whose conditions (path, host) match performs the rule's actions: authentication (if there is an authenticate action), then forward to a target group. Pick a scenario and send a request:

<AlbRuleSim client:visible />

Besides path and host, listener rules have four more condition types: **http-header**, **http-request-method**, **query-string** and **source-ip** (in CIDR form). Each rule has a priority; the ALB evaluates rules from the lowest priority value to the highest, stops at the first rule whose conditions all match, and always evaluates the default rule last. An action can be forward, **redirect** (301 or 302; HTTP to HTTPS is allowed, HTTPS to HTTP is not), **fixed-response** (returns a 2XX, 4XX or 5XX code at the ALB) or authenticate. Pick a request and see which rule handles it:

<RuleMatchSim client:visible />

<Takeaway>Listener rules route by path (`/orders/*`, the query string is not considered), host (`*.mftech.vn` matches `khuyenmai.mftech.vn` but not the apex domain `mftech.vn`), header, method, query string and source IP; a rule with a lower priority value is evaluated first. The HTTP :80 listener uses a redirect action to move clients to HTTPS. The ALB has no built-in request rate limiting: associate AWS WAF and use a rate-based rule (counts by source IP by default, evaluation window of 1, 2, 5 or 10 minutes, minimum limit of 10 requests). The ALB integrates authentication with Cognito.</Takeaway>

</Scene>

<p class="scene-intro">A load balancer routes requests only to targets in the healthy state; that state is determined by health checks sent periodically to each target.</p>

The ALB marks i-2 as unhealthy, while an engineer who connects to the instance over SSH confirms the application still works. The load balancer relies only on **health check** results: it calls a path on each target periodically (every 30 seconds by default for the instance or ip target type). <Scene id="en-s5" label="Part 5/7" title="SSL/TLS certificates for HTTPS listeners (SNI)" questions={["exam4_q40", "exam4_q57"]}>

<p class="scene-intro">Every HTTPS domain needs a certificate; when many domains share one load balancer, it needs a way to present the right certificate for each.</p>

MFTECH splits its system into microservices behind one ALB: `checkout.mftech.vn`, `www.mftech.vn`, plus `mftech.com.vn/profile` and `mftech.com.vn/search` for its second brand. Every URL must use HTTPS. The operations team considers four settings: one wildcard certificate, a list of certificates chosen by SNI, an HTTP to HTTPS redirect, and a different security policy. Each setting solves a different problem; change them one at a time and watch the result for every client:

<HttpsListenerSim client:visible />

An HTTPS listener always has one **default certificate**. When you add a certificate list, the ALB uses **SNI** to pick the certificate that matches the domain name the client requests; the default certificate is used only when the client sends no SNI or no certificate matches. A wildcard certificate `*.mftech.vn` protects only one subdomain level; it does not protect the apex domain `mftech.vn` or a different domain such as `mftech.com.vn`. A **security policy** is the combination of protocols and ciphers used to negotiate TLS between the client and the ALB: a listener created in the console defaults to `ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09` (TLS 1.3 and 1.2); one created with the AWS CLI or CloudFormation defaults to `ELBSecurityPolicy-2016-08` (TLS 1.0 to 1.2).

<Takeaway>Several different domain names over HTTPS on one ALB with minimal configuration: add certificates to the certificate list and let the ALB choose by SNI. A wildcard fits only when every name is a one-level subdomain of the same domain. An HTTP to HTTPS redirect only forces clients onto HTTPS; a security policy only decides protocols and ciphers. Neither adds a domain name to the listener.</Takeaway>

</Scene>

<Scene id="en-s6" label="Part 6/7" title="Gateway Load Balancers for third-party virtual appliances" questions={["exam3_q53", "exam3_q47", "exam6_q41"]}>

<p class="scene-intro">Some companies require all traffic to pass through security appliances such as firewalls; those appliances must also scale with load and be fault tolerant, just like the application tier.</p>

MFTECH's security team requires all internet traffic to the application to pass the firewall and IPS of a third-party vendor, running on EC2. The number of appliances must grow with the load and survive the failure of one appliance. A **Gateway Load Balancer** (GWLB) meets this requirement: it works at layer 3, accepts every IP packet on every port, exchanges traffic with the appliances using the **GENEVE protocol on port 6081**, keeps every packet of a flow on the same appliance (5-tuple by default), and sends traffic only to healthy appliances. The application in another VPC connects to the GWLB through a **Gateway Load Balancer endpoint** (a VPC endpoint powered by AWS PrivateLink), and route tables decide which traffic goes through that endpoint.

<GwlbSim client:visible />

<Takeaway>Deploy and scale a fleet of third-party appliances (firewalls, IDS/IPS, deep packet inspection) transparently: Gateway Load Balancer + GWLB endpoint, with route tables using the endpoint as the next hop. A GWLB does not parse HTTP and has no API keys or per-client request limits. A GWLB endpoint is billed hourly and per GB of data processed; it is not a path to S3 (S3 uses a gateway endpoint).</Takeaway>

</Scene>
