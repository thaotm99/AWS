After this incident, infrastructure needs to be **defined as code**, reviewed like code and reproducible exactly any number of times. **CloudFormation** meets this requirement for every type of resource; **Elastic Beanstalk** handles running web applications for teams that do not want to assemble each infrastructure component themselves.

<Scene id="en-s1" label="Part 1/3" title="Templates replace manual actions" questions={["exam4_q47", "exam4_q15", "exam4_q17"]}>

A **template** is a YAML or JSON file that describes the resources to create. CloudFormation reads the template and creates a **stack**: a group of resources that are created, updated and deleted together. To change the infrastructure, update the template and perform an **update stack**; a **change set** lets you preview the changes CloudFormation will apply. Run three ShopViet scenarios:

<StackSim client:visible />

Being able to read a template matters as much as being able to write one. Below is the web group's security group in ShopViet's template. Send each test connection to see the effect of each rule:

<SgRuleSim client:visible />

<Takeaway>Make sure every resource is created to the same standard: put the standard into a CloudFormation template and let users choose parameters only from an allowed list. Change infrastructure by updating the template and updating the stack. When creation fails midway, by default the stack rolls back automatically (you can choose to keep the resources that were created successfully). Using CloudFormation with resources in the AWS::*, Alexa::* and Custom::* namespaces incurs no additional charge; you pay only for the AWS resources created. SecurityGroupIngress is a security group inbound rule and supports allow rules only.</Takeaway>

</Scene>

<Scene id="en-s2" label="Part 2/3" title="Applying one standard to every account and Region" questions={["exam3_q36"]}>

ShopViet now has several accounts in **AWS Organizations**: production, dev, data, and soon a branch in Japan. Each account operates in several Regions. Every environment must use the approved EC2 types and the standard IAM role for Lambda. Deploy the baseline template with three approaches, then add a new account:

<StackSetSim client:visible />

<Takeaway>One template, many accounts and many Regions, one operation: CloudFormation StackSets. Turn on automatic deployment so that new accounts joining the OU receive the stack automatically. AWS RAM only shares existing resources; it does not deploy templates.</Takeaway>

</Scene>

<Scene id="en-s3" label="Part 3/3" title="Elastic Beanstalk: starting a new instance in 2 minutes" questions={["exam4_q1"]}>

ShopViet's main website runs on **Elastic Beanstalk**: the development team only uploads the code, and Beanstalk automatically creates the EC2 instances, load balancer and Auto Scaling group and monitors health. The team can still view and adjust the underlying resources. The problem is that installing the application takes 45 minutes: when traffic grows, Beanstalk adds instances, but new instances can only serve requests almost an hour later. Compare the timing of four startup approaches:

<BootTimeSim client:visible />

<Takeaway>A long installation slows down the startup of new instances: put the static part into a golden AMI (Beanstalk supports custom AMIs), and let user data create only the dynamic part at startup.</Takeaway>

</Scene>
