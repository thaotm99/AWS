Snowball Edge is **no longer available to new customers**. The Storage Optimized device has 210 TB of usable capacity. For new customers, AWS suggests DataSync for online transfers, **AWS Data Transfer Terminal** for physical transfers (bringing storage devices to an AWS facility; currently available only to Enterprise Support customers), or an AWS Partner solution.

<Takeaway>Bandwidth is sufficient: DataSync (can transfer privately over Direct Connect + a VPC endpoint). SFTP: Transfer Family. Existing objects that must be copied to another Region: S3 Batch Replication.</Takeaway>

With the "Drop tables on target" target table preparation mode, DMS creates only **tables, primary keys and in some cases unique indexes** on the target (basic schema migration); DMS does **not** create secondary indexes, foreign keys, nonprimary key constraints, column data defaults or user accounts. So when a database has secondary indexes, foreign keys and stored procedures: for the same engine, migrate the schema with native tools (Oracle SQL Developer, MySQL Workbench, pgAdmin 4); for a different engine, use **DMS Schema Conversion** (a DMS feature) or **AWS SCT** to convert tables, views, stored procedures and functions, then DMS migrates the data. For full load + CDC, AWS recommends leaving out indexes and referential integrity constraints during the full load, then pausing the task before the CDC phase to build the secondary indexes and referential integrity constraints before resuming.

The other options each miss part of the requirement. **DMS Standard** uses a replication instance (an EC2 instance that DMS creates in a VPC): the operations team must estimate capacity, pick an instance class and resize it as the load changes, which are exactly the tasks DMS Serverless removes; the replication instance is also not an EC2 instance in one of ShopViet's Auto Scaling groups that could take a scaling policy. AWS Glue (ETL) and Lambda have no built-in way to read the Oracle redo logs and replicate changes transaction by transaction; ShopViet would have to build the change capture itself.

<Takeaway>Servers: MGN (agent → test → cutover). Databases with a different engine: SCT (or DMS Schema Conversion) + DMS; DMS alone creates only tables and primary keys, not secondary indexes, foreign keys or stored procedures. SQL Server to Aurora PostgreSQL with minimal code changes: Babelfish. Existing data plus ongoing changes: the full load + CDC migration type (DMS reads the source transaction logs). A fluctuating volume of changes and no wish to size a replication instance: DMS Serverless (scales within the Min–Max DCU range).</Takeaway>

<Scene id="en-s4" label="Part 4/4" title="Managed SFTP with AWS Transfer Family" questions={["exam5_q62"]}>

<p class="scene-intro">Partners are used to sending files over SFTP; instead of running your own SFTP servers, a managed service keeps their workflow unchanged while storing files directly in AWS.</p>

Suppliers send price lists and documents to ShopViet over SFTP. Today this runs on two Linux EC2 instances, each with an Elastic IP that the suppliers allow in their firewalls; Linux accounts are created by hand with file-level permissions; the data sits on a shared file system mounted on both instances. ShopViet wants a managed service but must keep three properties: fixed IP addresses, connections only from supplier IPs, and file-level permissions.

**AWS Transfer Family** provides AWS-managed SFTP, FTPS, FTP and AS2 servers that store data in **Amazon S3** or **Amazon EFS**. There are three configuration decisions:

- **Endpoint type**: *Public*; *VPC hosted* with **Internal** access (reachable only through the endpoint's private IPs); or *VPC hosted* with **Internet Facing** access and an **Elastic IP** in each subnet (this type supports only SFTP and FTPS). Public endpoints cannot restrict traffic with security groups.
- **Source IP restriction**: a **security group** on the VPC hosted endpoint that allows only the listed IPs.
- **Storage and permissions**: with EFS, each user gets a **POSIX profile** (user ID, group ID, secondary group IDs) and an IAM role; EFS uses these IDs to check permissions on every file and directory. With S3, a user's permissions come from an IAM role and a session policy.

<SftpExchangeSim client:visible />

<Takeaway>Managed SFTP, fixed IPs for partners to allow in their firewalls, connections only from known IPs: Transfer Family with a VPC hosted, internet-facing endpoint (Elastic IPs) and a security group. Linux-style file-level permissions on a shared file system: EFS with a POSIX profile (UID/GID) per user. Transfer Family stores only to S3 or EFS; AWS WAF inspects only HTTP(S) requests and does not filter SFTP.</Takeaway>
