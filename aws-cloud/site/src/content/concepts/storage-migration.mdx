Snowball Edge hiện **không còn nhận khách hàng mới**. Thiết bị Storage Optimized có 210 TB dung lượng khả dụng. Khi target table preparation mode là "Drop tables on target", DMS chỉ tạo **bảng, primary key và trong một số trường hợp unique index** trên đích (basic schema migration); DMS **không** tự tạo secondary index, foreign key, constraint không phải primary key, giá trị mặc định của cột hay user account. Vì vậy, khi database có secondary index, foreign key và stored procedure: cùng engine thì chuyển schema bằng công cụ gốc (Oracle SQL Developer, MySQL Workbench, pgAdmin 4); khác engine thì dùng **DMS Schema Conversion** (tính năng của DMS) hoặc **AWS SCT** để chuyển đổi bảng, view, stored procedure, function, sau đó DMS di chuyển dữ liệu. Với full load + CDC, AWS khuyến nghị bỏ index và ràng buộc tham chiếu trong lúc full load, sau đó tạm dừng task trước pha CDC để tạo secondary index và ràng buộc tham chiếu rồi mới tiếp tục.

Các phương án khác đều thiếu một phần của yêu cầu. **DMS Standard** dùng replication instance (EC2 instance do DMS tạo trong VPC): người vận hành phải ước lượng capacity, chọn instance class và thay đổi kích thước khi tải thay đổi, đúng những tác vụ mà DMS Serverless loại bỏ; replication instance cũng không phải EC2 instance thuộc Auto Scaling group của ShopViet để gắn scaling policy. AWS Glue (ETL) và Lambda không có sẵn cơ chế đọc redo log của Oracle để sao chép thay đổi theo transaction; ShopViet sẽ phải tự xây dựng phần ghi nhận thay đổi.

<Takeaway>Server: MGN (agent → test → cutover). Database khác engine: SCT (hoặc DMS Schema Conversion) + DMS; DMS chỉ tạo bảng và primary key, không tạo secondary index, foreign key hay stored procedure. SQL Server sang Aurora PostgreSQL với mức thay đổi code tối thiểu: Babelfish. Dữ liệu hiện có và thay đổi liên tục: migration type full load + CDC (DMS đọc transaction log của nguồn). Khối lượng thay đổi biến động, không muốn chọn kích thước replication instance: DMS Serverless (tự scale trong khoảng Min–Max DCU).</Takeaway>

<Scene id="s4" label="Phần 4/4" title="SFTP được quản lý với AWS Transfer Family" questions={["exam5_q62"]}>

<p class="scene-intro">Đối tác quen gửi file qua SFTP; thay vì tự vận hành SFTP server trên EC2, có thể dùng một fully managed service giữ nguyên cách làm việc của đối tác nhưng lưu tệp trực tiếp vào AWS.</p>

Các nhà cung cấp gửi bảng giá và chứng từ cho ShopViet qua SFTP. Hệ thống hiện tại gồm hai EC2 instance Linux, mỗi instance có một Elastic IP để nhà cung cấp cho phép trên firewall của họ; tài khoản Linux được tạo thủ công và phân quyền theo tệp; dữ liệu nằm trên một shared file system được mount vào cả hai instance. ShopViet muốn chuyển sang dịch vụ được quản lý nhưng giữ nguyên ba đặc điểm: địa chỉ IP cố định, chỉ IP của nhà cung cấp được kết nối, và phân quyền theo tệp.

**AWS Transfer Family** cung cấp server SFTP, FTPS, FTP và AS2 do AWS quản lý, lưu dữ liệu vào **Amazon S3** hoặc **Amazon EFS**. Có ba quyết định cấu hình:

- **Loại endpoint**: *Public*; *VPC hosted* với access **Internal** (chỉ truy cập qua private IP của endpoint); hoặc *VPC hosted* với access **Internet Facing**, gắn **Elastic IP** tại từng subnet (loại này chỉ hỗ trợ SFTP và FTPS). Endpoint public không giới hạn được lưu lượng bằng security group.
- **Giới hạn IP nguồn**: **security group** gắn vào endpoint đặt trong VPC, chỉ cho phép các IP được liệt kê.
- **Lưu trữ và phân quyền**: với EFS, mỗi user được gán **POSIX profile** (user ID, group ID, secondary group ID) và một IAM role; EFS dùng các ID này để kiểm tra quyền trên từng tệp và thư mục. Với S3, quyền của user do IAM role và session policy quyết định.
