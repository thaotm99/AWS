<Scene id="s2" label="Phần 2/4" title="Vận hành Lambda trong môi trường production" questions={["exam4_q25", "exam1_q50", "exam3_q20", "exam6_q35", "exam4_q39", "exam2_q16"]}>

Một số vấn đề chỉ xuất hiện khi triển khai lên production: function gắn vào VPC không truy cập được Internet, người dùng chờ lâu vào giờ cao điểm, thông báo bị throttle khi vượt concurrency quota, mật khẩu database lưu trong cấu hình. Chọn từng tình huống, chạy thử, sau đó bật tuỳ chọn để khắc phục:

<LambdaRunSim client:visible />

Hai lưu ý bổ sung. Mỗi lần thực thi Lambda function tiêu chuẩn tối đa **15 phút** (900 giây; Lambda Managed Instances cho phép tới 90 phút với lời gọi bất đồng bộ hoặc qua event source mapping, trừ Amazon MQ và Amazon DocumentDB); job dài hơn nên chạy bằng container trên Fargate (bài Containers). Khi chưa gắn vào VPC, Lambda function vẫn gọi được Internet và các AWS API công khai; chỉ gắn VPC khi cần truy cập tài nguyên private như RDS, và khi đó cần NAT gateway như mô phỏng trên. Cách định cỡ memory, /tmp, timeout và đóng gói (layer, container image) được trình bày ở phần 3.

<Takeaway>Lambda trong VPC cần NAT gateway để truy cập Internet. Cold start vào giờ cao điểm: provisioned concurrency. Concurrency có quota theo account và Region; cấu hình alarm trên ConcurrentExecutions. Không lưu mật khẩu: IAM database authentication. Truy cập cross-account: cả execution role và bucket policy đều phải cho phép.</Takeaway>

</Scene>

<Scene id="sizing" label="Phần 3/4" title="Cấu hình tài nguyên và đóng gói function" questions={["exam4_q25", "exam3_q32", "exam1_q9"]}>

Mỗi Lambda function có một số thiết lập quyết định tài nguyên của execution environment:

- **Memory** từ 128 MB (mặc định) tới 10.240 MB. Lambda không có thiết lập CPU riêng: CPU được cấp **tỷ lệ với memory**, tại 1.769 MB function có tương đương một vCPU. Tác vụ nặng về CPU chạy chậm thì tăng memory. Chi phí duration tính theo GB-giây nên phụ thuộc memory đã cấp.
- **Ephemeral storage** (`/tmp`) từ 512 MB (mặc định) tới 10.240 MB, mã hoá khi lưu trữ bằng key do AWS quản lý. Dữ liệu trong `/tmp` **riêng cho từng execution environment** và chỉ là bộ nhớ đệm tạm: có thể còn lại khi môi trường được tái sử dụng, nhưng Lambda thu hồi môi trường sau vài giờ. Dữ liệu cần giữ lâu dài hoặc dùng chung giữa các function đặt trên Amazon S3 hoặc Amazon EFS.
- **Timeout** mặc định 3 giây, tối đa 900 giây. Timeout quá sát thời gian chạy dễ gây lỗi khi dữ liệu lớn hơn bình thường; timeout quá cao làm lời gọi bị treo giữ môi trường thực thi lâu hơn cần thiết. Giá trị phù hợp được xác định bằng load test.
- **Kiểu đóng gói**: tệp .zip (tối đa 250 MB khi giải nén, **kể cả layer**) hoặc **container image** lưu trong Amazon ECR cùng Region (tối đa 10 GB). **Lambda layer** chứa thư viện, custom runtime hoặc tệp cấu hình dùng chung cho nhiều function; mỗi function dùng tối đa 5 layer, mỗi layer version là bản chụp bất biến, và layer chỉ áp dụng cho function dạng .zip.

Thời gian khởi tạo (cold start) phụ thuộc kích thước package, gồm cả thư viện, dependency và layer. Đưa thư viện vào layer giúp package gọn và dùng chung được, nhưng không loại bỏ thời gian khởi tạo thư viện đó; cách giảm cold start là chỉ import những gì function cần, hoặc dùng provisioned concurrency (phần 2).

Chọn từng tác vụ của ShopViet, điều chỉnh cấu hình rồi triển khai thử:

<FunctionConfigSim client:visible />

Layer không thay thế được nơi lưu dữ liệu. Khi team gợi ý sản phẩm cần đọc bộ dữ liệu lớn, liên tục tăng trên EFS thuộc account đối tác, Lambda mount trực tiếp EFS đó qua access point, kèm file system policy cho phép cross-account và kết nối VPC peering: xem [bài Storage, phần 3](/concepts/storage/#s3). Đóng gói dữ liệu vào layer không phù hợp vì layer version bất biến và bị giới hạn 250 MB chung với package.

<Takeaway>CPU tỷ lệ với memory (1.769 MB ≈ 1 vCPU). `/tmp` từ 512 MB tới 10.240 MB, tạm thời, riêng cho từng execution environment; dữ liệu bền vững dùng S3 hoặc EFS. Timeout đặt theo load test, không đặt dư. Gói .zip tối đa 250 MB giải nén kể cả layer; lớn hơn dùng container image (tối đa 10 GB). Layer cho thư viện dùng chung, không cho dữ liệu.</Takeaway>

</Scene>

Ứng dụng mobile, đối tác bán hàng và trang quản trị đều gọi tới `api.shopviet.vn`. **API Gateway** thực hiện một chuỗi bước kiểm tra trước khi request tới mã ứng dụng. Chọn tình huống và gửi request:

<ApiGatewaySim client:visible />

Một số yêu cầu khác:

- Chat giữa người mua và người bán cần kết nối hai chiều, máy chủ chủ động đẩy tin nhắn tới client: **WebSocket API**. Với REST API, mỗi request độc lập và không duy trì kết nối.
- Shipper gửi vị trí liên tục để theo dõi đơn hàng (tình huống "Shipper gửi vị trí liên tục" trong mô phỏng): REST API dùng **AWS service integration** gọi thẳng `PutRecord` của Kinesis Data Streams, không cần Lambda trung gian, để **Amazon Managed Service for Apache Flink** (tên cũ: Amazon Kinesis Data Analytics) phân tích stream. Lambda chỉ xử lý từng request, không phải nơi lưu trữ hay phân tích dữ liệu.
- Tiếp nhận giao dịch từ ứng dụng, kiểm tra dữ liệu đơn giản rồi xử lý, với chi phí vận hành thấp nhất: **REST API + Lambda** kiểm tra dữ liệu, backend serverless phía sau. Không có máy chủ hay container nào cần vá lỗi.

Xác thực người dùng ở API Gateway có nhiều cơ chế. Ứng dụng mobile mới của ShopViet đăng nhập qua một identity provider bên ngoài tuân thủ OIDC; backend cần kiểm tra JWT và scope với độ trễ, chi phí thấp, không viết mã xác thực. **HTTP API với JWT authorizer** đáp ứng yêu cầu này: API Gateway kiểm tra chữ ký token bằng public key lấy từ `jwks_uri` của issuer, kiểm tra các claim `iss`, `aud`, `exp` và yêu cầu token có ít nhất một scope của route; các claim hợp lệ được chuyển tới backend. So sánh với các cơ chế còn lại:
